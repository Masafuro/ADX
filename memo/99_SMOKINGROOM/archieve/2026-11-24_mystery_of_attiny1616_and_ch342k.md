# ATtiny1616 + CH342K の謎――なぜ「UPDI じゃないとできない」のか

*2026-11-24（深夜の部）/ 喫煙所にて（本日2回目・441個目の `.md`、`.mdx` も足すと 446個目）*

今日の帰り際、雑談のつもりが妙に核心を突く話になったので、忘れないうちに灰皿の横へメモを残しておきます。

きっかけは、リポジトリの `hardware/archive/` に載せる間もなく消えていった、いくつかの未コミット試作ボード（`CH32X035` / `CH32V003` / `CH552` など）の話から。

> **「Arduino 的な USB 1 本開発が、なんか全然うまくいかないんだよ。回路的なブレイクスルーがないと CH32X035 をリリースできるところへ持っていけないんだろうと思う。振り返ると、`ATtiny1616-MNR + CH342K` はなぜかこれを解決できている。たぶん、半導体と MCU チップの限界めいたものを感じる。」**

掘ってみたら、これは気のせいでも設計の迷いでもなく、本当に **現代の MCU シリコン設計の「構造的な壁」** そのものでした。

---

## 1. そもそも「スケッチ書き込み」と「`Serial.print`」の両立に無理がある

冷静に役割を並べると、この 2 つは真逆の性質を持っています。

- **スケッチ書き込み（コントロールプレーン）**：患者に強制麻酔をかけて脳を入れ替える **外科手術**。スケッチが暴走・無限ループしていても、外から確実に叩き起こして書き換えられる必要がある。
- **`Serial.print`（データプレーン）**：起きている患者の独り言をリアルタイムに聴き続ける **聴診器**。CPU を止めずに垂れ流し続けたいし、聴き始めた瞬間に患者が気絶しても困る。

実際、`CORE-D` の開発中に **UPDI 1 本だけでデバッグできないか** さんざん試した結果も、まったく同じ壁に当たっています。

- UPDI 経由のメモリダンプ等はできても、結局 **CPU が止まってしまうため「動かしながらのデバッグ」ができない**。
- 物理世界と時間軸で動く組み込みでは、`Serial.print` のように「止めずに垂れ流せる独立した管」はやっぱり手放せない。

Arduino（2005年）が「1 本の UART ＋ DTR コンデンサ」で両方を 1 つの管に押し込む裏ワザを流行らせたせいで、20 年ものあいだ「モニタを開くと勝手にリセット」「ポート競合」「内蔵 USB での再列挙切れ → `while (!Serial);` で箱入れ後に永遠起動しない文鎮化」といった歪みが生まれ続けました。

そしてその必然の証拠が、**世界中の半導体メーカーの公式デバッガのピン配列** にそのまま出ています。

| 公式デバッガ／評価ボード | 書込・デバッグ線 | 並走する独立シリアル | 中に載っているデバッガ用 MCU |
| :--- | :--- | :--- | :--- |
| **WCH `WCH-LinkE`** | SDI (2線) | **`TX / RX`**（計 5 ピン構成） | CH32V305 等の 32bit MCU |
| **ST `ST-LINK` (Nucleo)** | SWD | **Virtual COM Port (`TX / RX`)** | STM32 系 32bit MCU |
| **Microchip `nEDBG` (Curiosity Nano)** | UPDI | **Virtual COM Port (`TX / RX`)** | SAMD21 (32bit MCU) |
| **Raspberry Pi `Debug Probe`** | SWD | **UART (`TX / RX`)** | RP2040 (32bit MCU) |

**全社が「書込線 1 本だけでは開発できない。横に独立した `TX/RX` を並走させるしかない」という同じ結論に収斂**し、そのためにわざわざ **もう 1 個立派な 32bit MCU** を載せて USB 1 本に束ねています。

## 2. なぜ他の MCU では詰まり、`ATtiny1616 + CH342K` だけ解けてしまうのか

「USB 1 本・ボタン操作なし・暴走しても復旧できる・シリアルモニタが切れない・しかも安く」を他の MCU で作ろうとすると、半導体の **2 つの壁** に正面衝突します。

### 壁①：内蔵 USB の「自分の脳外科手術」パラドックス
- `CH32X035` / `RP2040` / `STM32` / `CH552` などの USB 内蔵 MCU は、通常運転時の USB スタックが **ユーザースケッチと同じ CPU の中** で動いている。
- そのため 1200bps タッチ等のボタンレス書込はソフト側の協力が前提になり、スケッチがハングした瞬間に USB ごと死んで **物理 BOOT ボタン必須** へ逆戻りする（箱に入れると詰む）。
- とくに `CH32X035` は USB ROM ブート起動ピンが **`PC17`（＝USB の D+ そのもの）** と兼用なので、USB を繋いだまま自動でブートへ落とすのが電気的に極めて不格好。さらに書込のたびに USB が再列挙され、シリアルモニタも切れる。

### 壁②：ハードウェア書込ポートの「プロトコル格差」
- CPU がハングしていても外から叩けるハードウェア書込端子は、ARM が **SWD**、RISC-V が **JTAG**、WCH が独自 **SDI**。
- いずれもクロック同期や特殊タイミングのビットプロトコルなので、**安くて固定機能の USB-UART 変換 IC には絶対に喋れない**。
- 結果、外から確実に叩くには「2 個目のデバッガ MCU」を載せるしかなく、コストも工場での「書込機自身のファーム焼き」も破綻する。
- ※ 例外として、**ESP32 + CH340** は DTR/RTS＋トランジスタ回路で UART ROM ブートへ落とせるが 1 ポート共用の宿命が残り、**ESP32-C3/S3/C6** はシリコン内に CPU 独立のハードウェア USB-Serial/JTAG 回路を焼き込んで突破しているが、無線モジュール特有の技適・消費電力・ビルド重さという別世界の制約を背負う。

### そこをすり抜けた、地球の反対側 2 社の「奇跡の噛み合い」
`ATtiny1616 + CH342K` は、まったく別の会社が別の理由で作った 2 つのレア仕様が偶然噛み合った、半導体カタログ全体でもほぼ唯一のスイートスポットになっている。

1. **Microchip（旧 Atmel）の `UPDI`**：
   - フラッシュ上のブートローダではなく、**CPU が完全に死んでいても外から強制停止・リセット・消去・書換ができる本物のハードウェア書込ポート**。
   - なのに通信プロトコルが **ただの非同期 UART フレーム（1線半二重）**。おかげでファーム焼き不要の安物 USB-UART チップ＋抵抗 1 本が、そのまま **ハードウェアライタ（`SerialUPDI`）** に化ける。
2. **WCH の `CH342K`**：
   - ESSOP-10・クリスタルレス・数十セント・ファーム管理ゼロの固定機能 IC なのに、**独立 2ch の USB-UART** を 1 チップに収めている。
   - **Port 0 ＝ 常時生きているハードウェア書込機（UPDI）**、**Port 1 ＝ 絶対に切れない独立シリアルモニタ（`Serial.swap(1)`）** を USB 1 本の中で物理的に分離できる。

つまり `CORE-U` は、**Microchip が SAMD21 を丸ごと 1 個載せて実現している Curiosity Nano (`nEDBG`) 級の「ハードウェア書込＋独立 VCP」の二本柱を、\$0.40 の固定機能チップ 1 個・ファーム管理ゼロで裏口から再現してしまっている** ことになる。

かつて [hardware/CORE-U/rev0/concept.md](../../hardware/CORE-U/rev0/concept.md) に書かれていた

> *「ATtiny1616-MNR と CH342K の組み合わせでは Arduino IDE での開発時に、非常に不思議な感覚があった。すなわち、なにか開発しやすい。」*

あの「不思議な感覚」の正体は、安い 8bit ボードの見た目をしておきながら、足回りだけ業務評価ボード級の 2 系統分離になっていたことだった。

## 3. 世の中の盲点を証明する一次証言（Tindie の実ユーザー評）

しかもこの組み合わせ、驚くほど世の中で使われていない。今日 Tindie で見かけた `ATtiny1616` 開発ボードへの実ユーザーレビューが、その盲点をあまりにも綺麗に物語っていた。

> **Hugo | Sept. 27, 2024**
>
> Simple development board for a reasonable price, works well!
> Just as expected, a simple and easy-to-use development board around the ATTiny1616 processor. I needed to test this chip for a product that I am designing, and I am sure that this development board will work just fine for that. **The only downside is that my board (REV. C) has no serial port because the UART converter is used for UPDI programming. Suggestion for designer: maybe use a switch (with two signals/channels) for switching between programming mode and serial mode.** I cannot say anything about the communication since this sale was made without prior contact. Documentation has everything you might need.

製品設計のためにチップを評価している現役エンジニアですら、浮かぶ改善案は **「2 回路の物理スイッチで UPDI とシリアルを切り替えては？」** 止まりで、ボード側も `REV. C` に至るまで 1ch の `CH340N` クラスを UPDI 専用で積んだまま出荷している。

`CH342K` が広まっていない理由は、たぶん 3 つの思い込みの重なり：
1. **FTDI 時代（`FT2232H` / `CP2105`）の刷り込み**：2ch USB-UART は高くて大きくてクリスタル必須、という先入観。
2. **「USB-UART ＝ `CH340`（1ch）」の条件反射**：とりあえず 1ch を UPDI に繋いだ瞬間にチャンネルが埋まり、そこで思考が止まる。
3. **Arduino 時代の 1 ポート前提**：書込ピン（`PA0`）と UART（`PA1/PA2`）が物理的に別れた UPDI 世代で「2 つの独立 COM ポートを 1 本の USB で同時運用する」快感を、まだほとんどの人が体験していない。

## 4. 結び：`CORE-U` 再評価説（結論なし）

つい数時間前までは、`CORE-U` は「`CORE-A` より軽くてリスクが低い初戦機」くらいの立ち位置に見えていたのに、この謎をほどいた瞬間に風景がガラッと変わった気がします。

将来、Reddit や Hacker News で必ず飛んでくるであろう質問――
**「2026 年に、なぜ 32bit（RP2040 / CH32X035 / STM32）ではなく 8bit・16KB の `ATtiny1616` なのか？」**

これに対して、「単純な用途なら 16KB で十分だから」という守りの答えではなく、

> **「2 個目の 32bit デバッガ MCU を載せずに、ボタンレス・ハング耐性・シリアルモニタ常時接続を USB 1 本で物理的に両立できるのは、UART プロトコルで喋れるハードウェア書込ポート（UPDI）＋ 独立 2ch ブリッジ（CH342K）だけだから」**

という、**他の 32bit チップが物理的に真似できないシリコン由来の必然性** が丸見えになってしまいました。

「UPDI じゃないとできない」――これ、なかなか味わい深い再発見です。
