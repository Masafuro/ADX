(ADX Project Tone and Manner Guidelines)

## 1. はじめに：GitHub 公開リポジトリとしての ADX

ADX（Advanced Device eXtension）は、誰でも回路図を読み、コードをフォークし、自ら製造して現場で使える**完全なオープンソース・ハードウェア / ソフトウェアプロジェクト**です。

GitHub 上で公開開発を行う本リポジトリは、単なる「完成品のカタログ置き場」ではありません。世界中のメイカー、組込エンジニア、研究者が訪れる**「開かれた実験室（Open Workbench）」**です。

```text
［ 一般の企業・商用ハードウェア ］              【 ADX 公開 GitHub リポジトリ 】
  ・完成した製品のPRと宣伝                     ・リアルな実験ノート、失敗、試行錯誤の共有
  ・商業的バズワードや誇大広告                 ・回路定格、波形、BOM原価の誠実な開示
  ・「完璧」「無欠陥」と謳う                   ・物理的な限界とトレードオフの開示
  ・ユーザーは「消費者」                       ・読者は「未来の共同開発者・仲間」
```

ADX のコア精神である **「はたらくArduino（The Working Arduino）」**（机の上のプロトタイプを、現場のリアルな箱へ連れ出すための等身大の相棒）を具現化するため、本リポジトリで紡がれるすべての言葉・ドキュメント・対話は、本ガイドラインを基準として記述されます。

## 2. トーン＆マナー 4大原則 (Core Pillars)

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   【 ADX トーン＆マナー 4大原則 】                     │
│                                                                        │
│  1. 【 誠実な工学主義 】 (Engineering Integrity)                       │
│     物理法則と限界に忠実であること。絶対・ゼロ・完全を軽々しく言わない │
│  2. 【 親しみやすさ 】 (Accessible & Welcoming)                        │
│     高度な理論も難解にせず、日常の工作に根ざした言葉で語る             │
│  3. 【 明快な構造と動線 】 (Clarity & Navigation)                      │
│     結論ファースト、SSOTの徹底、図解による直感的な理解                 │
│  4. 【 建設的な対話文化 】 (Constructive Collaboration)                │
│     失敗や設計見直しを歓迎し、知見をオープンに共有する                 │
└────────────────────────────────────────────────────────────────────────┘
```

---

### 原則 1: 誠実な工学主義 (Engineering Integrity)
> **「物理法則と工学的な限界に常に忠実であること。誇張を排し、トレードオフを正直に開示する。」**

1. **絶対性・無謬性（むびゅうせい）を主張しない:**
   - 現実のハードウェアやファームウェアに「絶対」は存在しません。過剰な断定はエンジニアからの信頼を損ないます。
   - ✕「絶対に壊れない」「100%安全」「死なない」「完全無欠」
   - ◯「誤配線時にも破損リスクを極限まで低減」「フェイルセーフ設計」「波及ダメージの局所化」
2. **「ゼロ」「瞬時」などの非物理的表現を排除する:**
   - ジュール熱、半導体の過渡応答時間、リセット遅延など、物理的な制約を隠蔽しません。
   - ✕「自己発熱ゼロ」「0msで即時起動」「瞬時に100%遮断」
   - ◯「極小の自己発熱（密閉ケース内でも熱がこもらない）」「ブート待機遅延なし」「高速な過電流保護（マイクロ秒オーダー）」
3. **設計上のトレードオフ（割り切り）を堂々と語る:**
   - 「なぜ ATtiny1616 を 10MHz で動かすのか（3.3V安全動作領域と低発熱を優先したため）」
   - 「なぜ CH32X035 を選定したのか（USB PHY内蔵による劇的な原価低減と Flash/RAM 容量アップのため）」
   - 「何を捨てて、何を得たのか」を論理的・客観的に説明します。

---

### 原則 2: 親しみやすさ (Accessible & Welcoming)
> **「高度な理論や現場技術であっても難解にせず、直感的に伝わる言葉で語る。」**

1. **工学・回路理論の平易化:**
   - 差動伝送（RS-485）、ガルバニック絶縁、EMI対策、コプレーナ導波路構造などの専門技術であっても、数式だけで威圧するのではなく、「なぜその形なのか」「どうして安全なのか」を図解や平易な言葉で説明します。
2. **威圧的・軍事的なトーンの排除:**
   - 読者を威圧したり、恐怖心を煽る言葉遣いは使用しません。
   - ✕「重装甲」「鉄壁」「殲滅」「撲滅」「スレーブ（文脈によりエッジ/ノード/ペリフェラルに置換）」
   - ◯「現場に強い」「タフな」「信頼性の高い物理境界」「手間を大幅に削減」「エッジ端末」
3. **日常の工作・身近な現場に根ざした描写:**
   - 「重化学プラント」のような遠い世界だけでなく、「ガレージの換気扇連動」「家庭菜園の自動水やり」「店舗の間接照明」「3Dプリントケースに収めた自作ガジェット」など、メイカーが自分の日常として想像できる具体例を添えます。

---

### 原則 3: 明快な構造と動線 (Clarity & Navigation)
> **「ユーザーを迷わせない『明確な動線』と、主旨が一瞬で伝わる『明快な表現』を徹底する。」**

1. **結論ファースト（Conclusion First）:**
   - 回りくどい前置きを排し、「何ができるのか」「どう使うのか」「なぜこの設計なのか」の要点を冒頭で明示します。
2. **視覚的・構造的な直感性の担保:**
   - 長文テキストだけで説明せず、ASCII アート、ピン配置図、Mermaid フローチャート、対比表を積極的に活用します。

---

### 原則 4: 建設的な対話文化 (Constructive Collaboration)
> **「失敗や設計見直しを歓迎し、誰もが心理的安全を持って参加できる場を作る。」**

1. **Blameless（非難なき）カルチャー:**
   - バグ、設計ミス、仕様の不整合が発見された際、原因を個人の責任に帰するのではなく、「システムの改善機会」として歓迎し、冷静に対処します。
2. **コントリビューターへの敬意と歓迎:**
   - Issue や Pull Request でのフィードバックに対しては、まず参加してくれたことへの感謝を伝えます。
   - 「ここがダメだ」ではなく、「こうするとより安全になる」「このトレードオフはどう考えるか」という建設的な対話を心がけます。

## 3. ドキュメント構造規律：「仕様」と「説明」の疎結合 (Loose Coupling Architecture)

ドキュメントの長期的な保守性を維持し、仕様変更時の修正漏れ・不整合（Specification Drift）を撲滅するため、本プロジェクトでは**「仕様ドキュメント（Specification）」と「説明ドキュメント（Guides / Explanations）」を完全に疎結合**とします。

```text
┌────────────────────────────────────────────────────────────────────────┐
│               【 仕様ドキュメント (Specification: SSOT) 】              │
│  ・言語: 【 英語で統一 (English Only) 】                                │
│  ・格納先: `docs/spec/` 配下                                           │
│  ・役割: 厳密なピンアサイン、絶対定格、寸法、プロトコル規約の唯一の真実│
│  ・原則: 多言語展開しない。仕様変更時の変更箇所を「世界で1箇所」にする│
└────────────────────────────────────┬───────────────────────────────────┘
                                     │ 参照 (Link Only)
                                     ▼
┌────────────────────────────────────────────────────────────────────────┐
│            【 説明ドキュメント (Guides, Explanations, Blog) 】          │
│  ・言語: 多言語（日本語 `docs/ja/`、英語 `docs/en/`、各国語）          │
│  ・役割: 設計意図（Why）、工学的メリット、使い方、チュートリアルの解説 │
│  ・原則: 【 厳密なピン配置表や数値を複製・ハードコードしない！ 】      │
│          「マスター仕様は docs/spec/ を参照」とし、思想の解説に徹する │
└────────────────────────────────────────────────────────────────────────┘
```

### 3.1 仕様ドキュメント（Specification）の規律
1. **英語統一の原則 (English Single Source of Truth):**
   - 規格・仕様（例: `docs/spec/ADX_PINOUT.md`, 各種MCUマッピング）は、**すべて英語で記述・維持**します。
   - 仕様を多言語に翻訳して複製すると、仕様改訂時に必ずバージョンの不一致や翻訳の解釈ズレが生じるためです。
2. **変更箇所は「1箇所」に集約:**
   - ハードウェアや通信バスの仕様変更（例: Pinout v4.0 策定）が生じた場合、修正すべき SSOT ファイルは**該当する `docs/spec/` 内の英語ドキュメント 1 ファイルのみ**とします。

### 3.2 説明・解説ドキュメント（Guides）の規律
1. **数値・ピン配置表のハードコード禁止 (No Redundant Tables):**
   - 日本語解説ガイド（`docs/ja/`）やブログ原稿等において、**SSOT に記載されているピンアサイン一覧表や電気定格数値をそのまま丸ごとコピー＆ペースト（二重管理）してはなりません**。
   - 複製された表は、将来の仕様改訂時に「更新忘れ」となり、読者を混乱させる最大の原因になります。
2. **解説ドキュメントが果たすべき真の役割:**
   - 諸元・数値の提示は `docs/spec/` へのリンクに委ね、解説ドキュメントは**「なぜその設計にしたのか（Rationale）」「現場でどんな事故を防ぐのか」「どう配線すれば安全か」**といった、エンジニアリングの背景やストーリーの解説に注力します。

## 4. 具体的な用語・表現対比マトリクス (DO / DON'T)

ドキュメント執筆、コードコメント、Issue 作成時に参照すべき具体的な語彙対比表です。

| カテゴリ | ✕ 避けるべき表現 (DON'T) | ◯ 推奨される表現 (DO) | 理由・トーンの狙い |
| :--- | :--- | :--- | :--- |
| **安全性・保護** | 100% 完全保護 / 絶対に壊れない / PCが完全無傷 | **誤配線や過電流時にもPCへの波及リスクを極限まで低減** | 物理的な限界を弁え、PL法上のリスクを回避する誠実な記述。 |
| **機構・配線** | 振動でも絶対に緩みません | **長期間の激しい振動でも緩みにくく、定期的な増し締めが不要** | スプリングクランプ端子の実用的な優位性を正確に伝える。 |
| **熱・消費電力** | 自己発熱ゼロ / 発熱なし | **極小の自己発熱 / 密閉ケース内でも熱がこもりにくい極低発熱** | ジュール熱の存在を無視せず、ケース組み込み時の実用性を語る。 |
| **起動・応答時間** | 0msで即座に起動 / 瞬時に遮断 | **ブート待機遅延なし (Instant Boot) / 高速遮断保護（マイクロ秒オーダー）** | マイコンのPOR時間や半導体の応答遅延を踏まえた正確な工学表現。 |
| **耐熱・環境** | -40℃〜+105℃ 完全保証 | **主要部品に産業・車載グレード（-40℃〜+105℃）品を採用** | 基板完成品としての全数環境試験と誤認されるリスクを避ける。 |
| **製品の形容** | 重装甲スレーブ / 8-bitの戦士 | **高耐環境・高信頼エッジ端末 / 現場に強いタフなエッジ基板** | ミリタリー調の威圧感を排し、身近で頼もしい道具のイメージを与える。 |
| **構造・シールド** | 鉄壁の防壁 / 完璧なシールド | **信頼性の高い物理境界 / 厳格なコプレーナ・シールド構造** | 情緒的・誇張表現を排し、構造的メリットを論理的に説明する。 |
| **改善・作業** | スイッチ操作の完全撲滅 | **ケースを開けてスイッチを押す手間を大幅に削減** | 攻撃的な単語を排し、作業負担の軽減というポジティブな価値に変換。 |

## 5. ドキュメント階層別 適用ガイドライン

ADX リポジトリのドキュメントは、以下の4層構造で構成されています。それぞれの読者ターゲットに応じたトーンを適用します。

```text
┌────────────────────────────────────────────────────────────────────────┐
│  【 Layer 1: エントリー層 (README.md / docs/ja/README.md) 】            │
│  ・読者: 初学者、メイカー、一般エンジニア                              │
│  ・トーン: 「親しみやすさ」最優先。ワクワク感、安心感、等身大の活用例。 │
├────────────────────────────────────────────────────────────────────────┤
│  【 Layer 2: 共通仕様 (docs/spec/ [英語]) ＆ 解説 (docs/ja/ [多言語]) 】 │
│  ・仕様 (docs/spec/): 英語統一、SSOT。厳密で無駄のない規格定義。       │
│  ・解説 (docs/ja/, en/): 仕様と疎結合。設計意図・シールド構造の解説。   │
├────────────────────────────────────────────────────────────────────────┤
│  【 Layer 3: ハードウェア個別仕様 (hardware/CORE-A5/, CORE-CX5/ 等) 】 │
│  ・読者: PCBA製造委託者、回路設計者、電子エンジニア                   │
│  ・トーン: 「誠実さ」最優先。BOM原価、回路定格、トレードオフの開示。   │
├────────────────────────────────────────────────────────────────────────┤
│  【 Layer 4: ファームウェア・プロトコル (firmware/ / docs/memo/) 】     │
│  ・読者: ファームウェア開発者、ドライバ実装者                          │
│  ・トーン: 「決定論的・正確性」。情緒的修飾を排し、状態遷移・規約を記述│
└────────────────────────────────────────────────────────────────────────┘
```

## 6. GitHub 上でのコミュニケーション規範 (Issue, PR, Commit)

### 6.1 コミットメッセージのトーン
- **フォーマット**: Conventional Commits（`feat:`, `fix:`, `docs:`, `refactor:`, `chore:` 等）を推奨。
- **内容**: 「何をしたか」だけでなく、可能な限り「**なぜその変更が必要だったか（Why）**」を1行添えます。
- **情緒を排する**: 乱暴な表現や感情的な言葉（例: `fix stupid bug` ➔ `fix: resolve timing issue in UART break detection`）は避けます。

### 6.2 Pull Request および Issue での対話
1. **フィードバックは「コードや仕様」に向け、「人物」に向けない:**
   - ✕「あなたの設計は間違っています」
   - ◯「この回路構成だと、逆電圧印加時にダイオードの損失が大きくなる懸念があります。〇〇への変更はいかがでしょうか？」
2. **代替案をセットで提案する:**
   - 単に問題点を指摘するだけでなく、「こういうアプローチだとBOMコストも抑えられそうです」といった建設的な代替案を添えます。
3. **意思決定ログを残す:**
   - レビュー中の重要な合意事項や設計変更の理由は、必ず Issue / PR のコメント、または `memo/` 配下のレポートとして文書化して残します。

## 7. まとめ：「誠実さ」が世界中のエンジニアを惹きつける

オープンソース・ハードウェアの世界において、ユーザーや開発者が最も信頼するのは、耳当たりの良い宣伝文句ではありません。

- **「なぜその部品、そのピン配置を選んだのか」**
- **「どこまでを守れて、何が限界なのか」**
- **「失敗から何を学び、どう改良したのか」**

これらを **「仕様と説明を美しく疎結合に保ち、誠実で、親しみやすく、わかりやすい言葉」** で世界に向けてオープンにし続けることこそが、ADX を長く愛され、現場で選ばれ続ける本物のグローバルスタンダードへと育てる道です。
