## 1. エグゼクティブ・サマリー（結論と基本方針）

ADX が採用する独自フィールドネットワーク規格 **LN-485 (LIN-based RS-485 / BR32)** において、現場でのファームウェア書き込みおよび診断を想定し、市販の安価な USB-RS485 ドングルを用いた **「PC（WebSerial / Python）」** および **「Android スマホ（USB-OTG）」** からの直接通信検証を実施した。

### 主要な結論
1. **PC 環境（WebSerial / Python）の実証完了**:
   * Google Chrome / Edge 等の WebSerial API（GitHub Pages）および Python (pyserial) において、**41 トランザクション連続 100% 成功（エラー率 0.00%）** を達成し、完全に実用レベルに達している。
2. **市販ドングルによるスマホ（Android）直結の限界解明**:
   * Galaxy Note8（Android 9）等を用いた実機検証において、一度は完全同期・往復通信（32B / CRC OK）を達成したものの、**Android OS のタスクスケジューリング・USB 非同期バッファに起因するジッター（ミリ秒単位の揺らぎ）** により、決定論的な安定性を担保することは物理的に困難であると結論付けた。
3. **専用「LN-485 ドングル（スマートドングル）」の必然性と供給戦略**:
   * DMX512（DMX USB Pro）や CAN（CANable）の歴史が示す通り、OS のジッターを排除して現場でスマホ・タブレット対応を実現する唯一の正攻法は、**「USB と電線の間に小さなマイコンを挟む専用ドングル」** である。
   * しかし、初期リリースから専用ドングルの開発・製造を必須要件とすると、**ボード本体（Core-S / Core-D）の市場供給が遅延し、プロジェクトの機動性を損なう**。

### 今後の基本方針（フェーズ分けロードマップ）
* **【第 1 フェーズ（現在）】: PC 軸（GitHub Pages Web Flasher / Python）での先行リリース**
  * BR32 / LN-485 の妥協なき耐ノイズ性を堅持。
  * 「ブラウザを開くだけでインストール不要で使えるオープンソース設備コントローラー」として世に出し、ボードの普及とエコシステム立ち上げを最優先とする。
* **【第 2 フェーズ（コミュニティ形成期）】: 現場ユースケースの蓄積**
  * 舞台演出、建築照明、展示、屋外センシングなどの実際の現場において、ユーザーがどのような運用・保守を求めているかを検証。
* **【第 3 フェーズ（スケール期）】: 満を持して「公式 LN-485 ドングル」を製品化**
  * 需要が確立した段階で、Core-D をベースとしたスマートドングル（または Wi-Fi/Bluetooth 設備ブリッジ）を公式アクセサリとしてリリースし、スマホ・タブレット完全対応を果たす。

## 2. 実機検証の経緯と到達点

### 2.1 PC 環境（GitHub Pages / Python）での成功
* **検証環境**: Windows / Linux / macOS 上の Google Chrome / Microsoft Edge（WebSerial API）および Python 3 (`pyserial`)。
* **実績**:
  * 9,600 bps での `0x00` 送出による LIN BREAK 生成と、19,200 bps への動的切り替えによる `0x55` (Sync) ＋ 32B BR32 フレーム送出。
  * `ser.flush()` / WebSerial の `writer.close()` により、OS カーネルがドングルの送信完了（TEMT: Transmitter Empty）を厳密に捕捉。
  * **合計 41 トランザクション連続 100% 成功、CRC エラー 0 件**（`firmware/bootloader/PLAN/BR32/WU/WU5_1_web_break_probe/WU5_1_REPORT.md` 参照）。

### 2.2 Android スマホ（USB-OTG）での挑戦
* **検証環境**: Samsung Galaxy Note8 (Android 9 / ARM64), CH340 / SP485 搭載 USB-RS485 ドングル, 専用診断アプリ（`adx-break-probe-android`）。
* **検証経過**:
  * **第 1 回試験**: パラメータ探索を実施。P10（15ms待機）にて 1/3 回の同期成立（部分受信）を確認。
  * **第 2 回試験**: UI 最適化および連続ストレステストを実施。サイクル `#11/20` において、**100% PERFECT（rx:32B, b0:0x01, b1:0x41, RTT:175.8ms, CRC OK）** を捉え、Android USB-OTG から ATtiny1616 の LINAUTO ハードウェアを貫通できる物理的成立性を実証。
  * **第 3 回・第 4 回試験**: メトロノーム（500ms スロット）を導入して Soft-UART の衝突を完全に解消。しかし、Android の `bulkTransfer` は USB RAM 転送完了時点でリターンするため、電線送出完了を検知できず、`Thread.sleep()` の長短によって **タイムアウト（沈黙）** または **ビットスリップ（Byte[0] = 0x40 化）** が間欠的に発生。再現性を 100% に高めることができなかった。

## 3. 技術的・物理的真因の徹底分析

なぜ PC では動き、Android では安定しなかったのか？ その真因はソフトウェアの不具合ではなく、**「物理レイヤ・情報理論・40 年のコンピュータ史」** に根ざした構造的制約にあった。

### 3.1 数理的制約：8N1 と LIN BREAK のギャップ
* **8N1 の限界**: Start(1) + Data(8) = **最大 9 ビット時間しか LOW を維持できない**（Stop ビットは必ず HIGH）。
* **LINAUTO の要求**: ATtiny1616 が Break と認識する閾値は **11 ビット時間以上の連続 LOW**。
* **比率の壁**:
  $$\frac{9\,\text{bits}}{11\,\text{bits}} \approx 0.818 \quad (18.2\%\,\text{以上のボーレート差が必要})$$
* ATtiny1616 の `LINAUTO` 同期許容範囲は LIN 規格上 **約 ±15%** であるため、ホストが 19,200 bps のまま 8N1 で `0x00` を送っても、Break としては絶対に受け付けられない。
* したがって、ホストは「9,600 bps にボーレートを落として Break を作り、直後に 19,200 bps に戻す」という **動的ボーレート変更トリック** を強いられる。

### 3.2 構造的ペア：Out-of-Band（文法外）と耐ノイズ性の二律背反
* **LIN BREAK は「文法外（Out-of-Band）」**:
  * 8N1 のルール上、正規の送信機からは絶対に発生し得ない「11ビット以上連続 LOW」という異常状態をあえて使うことで、過酷なサージ・ノイズ環境下でも誤認されない絶対的な耐性を獲得している。
  * しかし、**「通常の文法体系の外にある」ということは、通常の UART 送信ハードウェア（市販ドングル）にとっても「正規の手段では送れない」という裏返し** である。
* **マジックパケットは「文法内（In-Band）」**:
  * どんな USB ドングルでも 100% 確実に送れるが、ノイズの入る物理世界では確率的に偶発発生するリスクを原理的にゼロにできない。

### 3.3 ハードウェア自律遮断（門前払い）の価値
* `LINAUTO` モードの ATtiny1616 は、11 ビット以上の LOW（Break）を検知するまで、電線上にどれだけ激しいノイズや他ノードの通信が流れても、**CPU に受信完了割り込み（`RXCIF`）を 1 回たりとも上げない（CPU 負荷 0%）**。
* これを安易に「標準 UART のマジックパケット方式」にダウングレードすると、1 バイト届くたびに CPU 割り込みが発生し、**Interrupt Storm（割り込みの嵐）によってメインのリアルタイム制御ループ（照明・モーター・センシング）が破壊される**。
* したがって、マイコン側の LINAUTO という「シリコンの防壁」は絶対に堅持すべきである。

### 3.4 40 年のコンピュータ史が教える「OS ジッターの罠」
* **古の MODBUS RTU（1979年〜1990年代）**:
  * MS-DOS 時代、CPU は ISA バス直結の UART レジスタ（NS16550A 等）を直接 `OUT` 命令で叩き、送信完了（TEMT）を 1 マイクロ秒の狂いもなく監視できた。OS が存在しなかったからこそ、物理的な時間（3.5 文字の無音）を支配できた。
* **現代のマルチタスク OS と USB パケット化**:
  * 現代の OS（Windows, Android）は仮想化・パケット化されており、USB は 1ms 単位のフレームスケジュールで動く。
  * アプリが「電線に信号が出た瞬間」を知ることは不可能であり、`sleep()` は OS の気分次第でミリ秒単位でブレる。
* **舞台照明 DMX512 の教訓**:
  * 2000年代初頭、マイコンなしの安価な FTDI ドングルで PC から BREAK を打とうとした **「DMX USB Open」** は、OS の負荷で舞台照明が激しくチラつく（フリッカー）大惨事を引き起こし、プロの現場から追放された。
  * オーストラリア ENTTEC 社が **「FTDI の隣に小さなマイコン（Atmega）を 1 個載せた『DMX USB Pro』」** を開発したことでフリッカーは完全にゼロになり、世界標準となった。
* **CAN（Controller Area Network）の真実**:
  * 世の中に存在する USB-CAN ドングル（CANable, PCAN 等）は、1 つの例外もなく **STM32 等のマイコンを内蔵したスマートドングル** である。UART チップ単体でビット調停を行うことは物理的に不可能だからである。

| 方式 | 構成 | メリット | デメリット・課題 | 判定 |
| :--- | :--- | :--- | :--- | :---: |
| **案 1: 市販ドングル直結（Android）** | スマホ ＋ 市販 300 円ドングル（CH340） | ハードウェア追加費用ゼロ。 | Android OS のジッターにより、`sleep()` のタイミングが安定せず、通信成功率が 100% にならない。 | **現状見送り** |

## 5. 製品化戦略ロードマップ

```text
  【Phase 1: PC 先行リリース（現在）】
    ・BR32 / LN-485 の妥協なき耐ノイズ性を堅持
    ・GitHub Pages (WebSerial) による「ブラウザ型 Web Flasher」の完成
    ・Python CLI ツールの提供
    ・ADX Core-S / Core-D ボード単体での早期リリースと開発者コミュニティ形成
          │
          ▼
  【Phase 2: 現場フィードバックと市場開拓】
    ・舞台演出、建築照明、設備制御、屋外センシングでの実運用
    ・現場保守におけるスマホ・タブレット操作の具体的ニーズの把握
          │
          ▼
  【Phase 3: 公式 LN-485 スマートドングルの投入】
    ・Core-D ベースの「ADX Master ドングル（Type-C 接続）」を製品化
    ・Android / iOS アプリの正式展開（115,200 bps 固定・100% 決定論的動作）
    ・ワイヤレス（Wi-Fi / BLE 搭載ゲートウェイ）への水平展開
```

### 本判断のビジネス・開発的意義
1. **「リリース遅延の完全回避」**:
   * 専用ドングルのハードウェア設計・量産を待つことなく、完成済みのボード（Core-D / Core-S）を最速で市場に投入できる。
2. **「圧倒的な開発体験の提供」**:
   * 専用アプリをインストールさせる既存の産業機器に対し、「Chrome で URL を開くだけで書き込める Web Flasher」は、開発者・クリエイターにとって極めて魅力的な武器となる。
3. **「将来の拡張性の担保」**:
   * LN-485 / BR32 のプロトコル規格は一切妥協せずに保護されているため、Phase 3 でドングルを投入した際、過去に配備されたすべての ADX ノードが無改造のままスマホ対応可能となる。
