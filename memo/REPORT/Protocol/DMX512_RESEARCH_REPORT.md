# 調査レポート: DMX512 通信プロトコル詳解
〜 「再送もCRCも捨て去る」極限の割り切りが生んだ、舞台演出の絶対支配者 〜

---

## 1. エグゼクティブ・サマリー

**DMX512**（正式規格名: ANSI E1.11 - USITT DMX512-A）は、1986年に USITT（米国劇場技術協会）が策定した、エンターテインメント照明・舞台演出制御の世界的標準プロトコルです。

世界中の劇場、アリーナコンサート、スタジアム、テーマパーク、クラブ、さらには噴水やプロジェクションマッピングの連動に至るまで、**「光や演出機器を動かす現場の 100%」** がこのプロトコルで駆動されています。

DMX512 の最大の特徴は、一般的な通信プロトコルが血眼になって実装する **「確認応答（ACK）」「再送制御（ARQ）」「CRC エラー検出」をすべて完全にゴミ箱に捨て去ったこと** にあります。  
「半二重共有バス（RS-485）をあえて片道通行で使い倒し、ひたすら最新値を秒間 44 回垂れ流し続ける」という極限の割り切りによって、フリッカーのない完璧なリアルタイム照明演出を実現しています。

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                         【 DMX512 の 4 大特徴 】                            │
│                                                                             │
│  1. 【完全片道ストリーミング】: スレーブは送信回路すら持たない（衝突ゼロ）   │
│  2. 【超高頻度リフレッシュ】  : 最大 512 チャンネルの生データを秒間 44 回連射 │
│  3. 【信頼性保証の完全放棄】  : 「22ms 後に次が来るから、壊れたら捨てろ」   │
│  4. 【暗黙的アドレッシング】  : パケット内にアドレス不要。何バイト目かで判定│
└─────────────────────────────────────────────────────────────────────────────┘
```

## 2. システム構成とバス構造（Unidirectional Simplex）

DMX512 は、物理層に **RS-485（差動2線式）** を採用していますが、通信形態は **完全な一方向（Simplex / Unidirectional）** です。

```text
                     ┌───────────────────────────────────┐ RS-485 (Data+ / Data-)
                     │  ┌────────────────────────────────┼───┐
                     │  │                                │   │
              ┌──────┴──┴──────┐                  ┌──────┴──┴──────┐
              │ DMX Controller │                  │ Moving Light 1 │
              │   (照明卓)     │                  │  (Ch 1〜16)    │
              │  [TX のみ保有] │                  │  [RX のみ保有] │
              └────────────────┘                  └────────────────┘
                                                           │
                                                  ┌────────┴──┴──────┐
                                                  │ LED Dimmer 2     │
                                                  │  (Ch 17〜20)     │
                                                  │  [RX のみ保有]   │
                                                  └──────────────────┘
```

### 2.1 バスの特徴と制約
- **送信者（Master）は厳密に 1 台のみ**:
  照明卓や DMX インターフェースが送信機（TX）のドライバーを常時 ON にしてパケットを送り続けます。
- **受信者（Slave）は送信権を持たない**:
  ムービングライトや調光器（Dimmer）は、受信機（RX）しか持ちません（物理的に TX 回路が省かれている製品も多数あります）。
- **バス調停が「原理的に存在しない」**:
  スレーブが 1 ビットも発言しないため、**バス衝突（Collision）という概念そのものが存在しません**。
- **Universe（ユニバース）の概念**:
  1 本の物理バスで制御できる単位を「1 Universe（＝ 512 チャンネル）」と呼びます。巨大なフェスなどで数万個の LED を制御する場合は、バスの線を 10 本、100 本と並列に引き回します（近年は Art-Net や sACN という Ethernet 経由で多重伝送するのが主流）。

## 3. 物理層とパケットタイミング（250 kbps, 8N2）

### 3.1 物理仕様一覧
- **伝送速度**: **250,000 bps (250 kbps)** 固定（1ビット ＝ $4.0\,\mu\mathrm{s}$）
- **文字フォーマット**: **8N2**（1 Start, 8 Data, **2 Stop bits**, パリティなし）
  - 1 文字（スロット）の伝送時間 ＝ $11 \times 4.0\,\mu\mathrm{s} = \mathbf{44.0\,\mu\mathrm{s}}$
- **コネクタ**: XLR 5ピン（または安価な機器では XLR 3ピン）。終端抵抗 120Ω。

### 3.2 パケットシーケンス（Break ➔ MAB ➔ Start Code ➔ 512 Slots）

DMX512 の 1 パケット（パケットというより「1フレーム」）は、以下の厳密なタイミング波形で始まります。

```text
       Break (Low: 88μs以上)     MAB (High: 8μs以上)
    ┌──────────────────────┐  ┌───┐
    │                      │  │   │
────┘                      └──┘   └───[Start Code]───[Slot 1]───[Slot 2] ... [Slot 512]───
     (Framing Error 発生)      (Mark)   (0x00)          (Ch 1)     (Ch 2)        (Ch 512)
```

| 構成要素 | バス状態 | 規定時間（標準） | 役割と動作仕様 |
| :--- | :---: | :---: | :--- |
| **Break** | **Low** | **$88\,\mu\mathrm{s}$ 以上**<br>(通常 $100\sim176\,\mu\mathrm{s}$) | **物理層違反によるフレーム開始合図**。<br>UART の 1 文字時間（$44\,\mu\mathrm{s}$）を大幅に超える長さの Low を印加し、受信マイコンに意図的に **「Framing Error」** を発生させる。 |
| **MAB** | **High** | **$8\,\mu\mathrm{s}$ 以上**<br>(通常 $12\sim16\,\mu\mathrm{s}$) | **Mark After Break**。<br>Break 直後の High パルス。マイコンがエラー処理を終え、次に来る Start ビットを受信できるように状態をリセットする。 |
| **Start Code** | データ | $44.0\,\mu\mathrm{s}$ (1B) | **データの種別コード**。<br>通常の照明演出データは **`0x00` 固定**。後述する RDM やメーカー独自データでは別の値が入る。 |
| **Slot 1〜512** | データ | 各 $44.0\,\mu\mathrm{s}$<br>(最大 512B) | **各チャンネルの調光値（`0x00`〜`0xFF`: 0〜255）**。<br>各バイトの間に任意のマーク時間（MTBF: 0〜1秒）が挟まってもよい。 |

## 4. なぜ「秒間 44 回」なのか？（人間の目と時間割）

DMX512 のフレーム長とリフレッシュレートは、数学的かつ生理学的に極めて美しく設計されています。

### 4.1 フルフレーム（512チャンネル）の所要時間計算
$$
\begin{aligned}
T_{frame} &= T_{Break} + T_{MAB} + T_{StartCode} + (512 \times T_{slot}) \\
&= 100\,\mu\mathrm{s} + 12\,\mu\mathrm{s} + 44\,\mu\mathrm{s} + (512 \times 44\,\mu\mathrm{s}) \\
&= 156\,\mu\mathrm{s} + 22,528\,\mu\mathrm{s} \\
&\approx \mathbf{22.68\,\mathrm{ms}}
\end{aligned}
$$

### 4.2 リフレッシュレート（更新周波数）
$$
f_{refresh} = \frac{1}{22.68\,\mathrm{ms}} \approx \mathbf{44.09\,\mathrm{Hz}}
$$

- **人間の知覚限界（フリッカーフリー）**:
  映画（24 fps）、テレビ（30 fps / 60 fps）を上回る **44 Hz の滑らかさ** で照明のフェードイン/フェードアウトが実行されます。人間の目にはカクつきが一切知覚できません。
- **チャンネル数が少なければさらに高速化**:
  もし接続されている機器が 100 チャンネル分しかない場合、512 バイトまで送らずに 100 バイトで打ち切って次の Break を送出することが規格上認められています。この場合、**100 Hz を超える超高速リフレッシュ** が可能になります。

## 5. DMX512 の狂気的哲学: 「最新値こそが正義」

普通のネットワークエンジニアが DMX512 の仕様書を見ると、以下の点で驚愕します：
1. **パケットに CRC もチェックサムもない**
2. **スレーブからの ACK（受領通知）が一切ない**
3. **パケット再送（Retry）の仕組みが皆無**

### なぜこれで 40 年間世界が回っているのか？

> **「1回分のパケットがノイズでビット化けしたところで、たった 22 ミリ秒後には最新のパケットが上書きされるから、何の問題もない。」**

舞台照明の世界において、**最悪の事態は「通信が詰まって照明の動きが一瞬止まること（ジッタの発生）」** です。  
もし CAN や TCP のように「エラーが起きたから再送する」という仕組みを入れてしまうと、再送待ちの間に時間割が遅延し、音響や映像との同期がミリ秒単位でズレてしまいます。

DMX512 は、**「メッセージ伝達の信頼性（Reliability）」を完全にかなぐり捨て、「時間軸の均一性（Isochronous / Determinism）」に全振りしたプロトコル** なのです。

## 6. 暗黙的アドレッシング（Implicit Addressing）の妙技

DMX512 には、**「パケットの中にノードの宛先アドレス（Node ID）が含まれていない」** という巨大な特徴があります。

### どうやって自分のデータだと識別するのか？
末端機器（ムービングライト等）の背面には、DIP スイッチや液晶パネルで **「DMX Start Address」**（例: `33` 番）が物理的に設定されています。

```text
照明卓送信: [StartCode] [Slot 1] ... [Slot 32] [Slot 33] [Slot 34] ... [Slot 48] ...
                                                  │         │              │
ムービングライト (Ch 33〜48 設定):               ├──Pan─── ├──Tilt── ...  └──Color─┤
(※Break受信後、UART受信割り込みをカウントし、33番目から16バイト分だけを自分のメモリに取り込む)
```

- **メリット**:
  パケット内に「宛先ヘッダー」が一切存在しないため、**通信オーバーヘッドが驚異のゼロ（512バイト中512バイトが純粋なデータ）**。
- **マイナス面**:
  機器ごとに人間がディップスイッチでアドレスの重複やズレがないように計算して設定しなければならず、現場設営でのヒューマンエラーの温床となる。

## 7. 後付けの双方向化と苦悩: RDM（ANSI E1.20）の教訓

DMX512 の「片道通行・アドレス手動設定」に現場が悲鳴を上げ、2006年に策定された拡張規格が **RDM (Remote Device Management)** です。

### RDM のアプローチ
- 従来の DMX512 と全く同じ RS-485 差動バスを使用。
- Start Code に `0xCC` を指定することで、「これは RDM パケットだ」と宣言。
- 照明卓からスレーブに対して「お前の UID は何だ？」「センサー温度は何度だ？」と問い合わせを行い、**スレーブが一時的に TX ドライバーを有効にして返信する（半二重双方向化）**。

### RDM が直面した「泥沼の現実」
片道通信だった DMX に双方向通信を持ち込んだ結果、まさに MODBUS や一般の RS-485 が直面した問題が一気に噴出しました：
1. **スプリッター/リピーターの全滅**:
   舞台現場にあった数千台の「DMX スプリッター（単なる片道バッファIC）」が、スレーブからの返信を通過させられず、高価な双方向対応 RDM スプリッターへの買い替えが必要になった。
2. **Auto-DE やターンアラウンド時間との戦い**:
   スレーブが返信するまでの遅延時間（Turnaround Time）のばらつきにより、照明卓側でのパケット先頭欠落トラブルが多発した。

## 8. LM-32 設計への示唆・対比

DMX512 の極端なアーキテクチャから、ADX の **LM-32** が学ぶべきポイントを整理します。

| 比較項目 | DMX512 | ADX LM-32 | 設計思想の違いと示唆 |
| :--- | :--- | :--- | :--- |
| **通信の性質** | **完全な状態ストリーミング**<br>(State Streaming) | **巡回メッセージング ＋**<br>**専有ストリーミング (2大系統)** | LM-32 の Streaming 系（第7章）は、まさに DMX の「高速連続連射」の思想。 |
| **エラーへの態度** | **無視・上書き**<br>(CRC なし、ACK なし) | **厳格な CRC16 ＋**<br>**CRC Error レスポンス** | モーターの安全停止や OTW（FW更新）を行う ADX では、DMX のような「壊れても上書き」は許されない。CRC16 は必須。 |
| **アドレッシング** | **暗黙的（スロット順序）**<br>(パケット内に ID なし) | **明示的（PUB_ID / SUB_ID）**<br>＋ **TOPIC_ID** | LM-32 は Pub/Sub モデルを採用。順序依存ではなく、データの内容（Topic）で識別するため自由度が高い。 |
| **フレーム同期** | **Break (Low長引き) ＋ MAB**<br>(UART Framing Error 依存) | **バイト同期 (`0x55 0xAD`)**<br>(標準 8N1 バイト列) | DMX の Break は USB ドングルや WebSerial で生成・検知するのが困難。LM-32 の「UART を破らない」設計の正しさが際立つ。 |
| **リフレッシュ周期** | 約 44 Hz（22.6ms 周期） | 10ms 〜 45ms (スロット周期) | LM-32 の 115,200bps・10ms タイムスロットは、DMX512（22ms）と同等以上のリアルタイム性を実現可能。 |

## 9. 結論

DMX512 は、**「通信における信頼性とは何か？」** という問いに対して、最も過激な回答を出したプロトコルです。

- **一般的な通信の常識**: 「パケットが失われたら、再送してでも確実に届けるべきだ」
- **DMX512 の常識**: **「古くなったデータを再送するくらいなら、捨てて新しいデータを送れ」**

ADX において、ファームウェア書き込み（OTW）やリレーの安全制御などの「1ビットの誤りも許されない領域」では MIL-STD-1553B や LM-32 のような厳格な CRC と確認応答が不可欠です。  
しかしその一方で、**「リアルタイムのセンサーテレメトリ垂れ流し」や「多軸モーターの速度指令」といった領域においては、DMX512 が体現した『状態ストリーミング（最新値上書き）思想』が極めて有効な武器になります。**

LM-32 の仕様書（第7章）で「Polling系」と「Streaming系」の2大系統を明示的に分けた判断は、まさにこの **「1553B 的な信頼性」と「DMX512 的な即時性」を単一のバス上で使い分けるための、極めて先進的な設計** であると言えます。
