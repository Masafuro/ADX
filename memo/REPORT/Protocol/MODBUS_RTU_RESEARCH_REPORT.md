# 調査レポート: MODBUS RTU 通信プロトコル詳解
〜 産業界の絶対標準（グランドファザー）の光と影、そして LM-32 が乗り越えるべき壁 〜

---

## 1. エグゼクティブ・サマリー

**MODBUS** は、1979年に米国の PLC（プログラマブル・ロジック・コントローラ）メーカーである Modicon（現シュナイダーエレクトリック）が策定したシリアル通信プロトコルです。

誕生から 45 年以上が経過した現在でも、工場の自動化（FA）、ビル管理システム（BMS）、太陽光発電インバータ、電力計、空調制御、各種産業用センサーに至るまで、**「RS-485 シリアルバスにおける事実上の世界共通言語（デファクトスタンダード）」** として君臨し続けています。

しかしその一方で、MODBUS RTU は **「1970年代の専用マイコン・純粋なリアルタイム処理」** を前提として設計されたため、現代の **「USB シリアル変換ドングル」「マルチタスク OS（Windows/Linux）」「ブラウザ WebSerial」** という環境において、無数のエンジニアを悩ませる深刻な構造的欠陥（特に **T3.5 タイマー問題**）を抱えています。

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                       【 MODBUS RTU の 4 大特徴 】                          │
│                                                                             │
│  1. 【極限のシンプルさ】: レジスタを読み書き（CRUD）するだけの直観的モデル  │
│  2. 【世界最高の普及率】: どんな産業用機器も Modbus さえ喋れれば接続可能   │
│  3. 【無通信時間による同期】: 「3.5文字分の静寂（T3.5）」でパケット境界を判定│
│  4. 【可変長フレーム】: 最大 256 バイト。ただしヘッダーに Length が存在しない│
└─────────────────────────────────────────────────────────────────────────────┘
```

## 2. システム構成とバス調停（Master / Slave モデル）

MODBUS RTU は、RS-485（差動2線式・半二重）共有バス上で動作する典型的な **集中制御・ポーリング型プロトコル** です。

```text
                 ┌──────────────────────────────────────┐ RS-485 差動バス (A/B)
                 │  ┌───────────────────────────────────┼───┐
                 │  │                                   │   │
           ┌─────┴──┴─────┐                       ┌─────┴──┴─────┐
           │ Master (PLC) │                       │ Slave (Node 1)│
           │ (唯一の発言権)│                       │ (温度センサー) │
           └──────────────┘                       └──────────────┘
                                                        │
                                                  ┌─────┴──┴─────┐
                                                  │ Slave (Node 2)│
                                                  │ (インバータ)   │
                                                  └──────────────┘
```

### 2.1 トランザクション原則
1. **シングルマスター・マルチスレーブ**:
   - バス上に Master は **厳密に 1 台のみ**。
   - スレーブは最大 **247 台**（アドレス `1`〜`247`。`0` は全体同報ブロードキャスト、`248`〜`255` は予約）。
2. **Request-Response（問われた時のみ発言）**:
   - スレーブが自発的にデータを送ることは一切許されません。
   - Master から「要求（Request）」が届いたスレーブのみが、一定時間内に「応答（Response）」を返送します。
3. **スレーブ間通信（P2P）の完全欠如**:
   - スレーブ 1 のデータをスレーブ 2 が知るためには、必ず Master が一度スレーブ 1 から吸い上げ、改めてスレーブ 2 に書き込む必要があります（バス帯域の二重消費）。

## 3. データモデル（4つのメモリ空間）

MODBUS がここまで普及した最大の理由は、PLC の内部メモリ構造をそのままプロトコルに落とし込んだ **「極めて分かりやすい 4 つのメモリ空間（テーブル）」** にあります。

| メモリ種別 | 通称 | アクセス権 | データ幅 | 主な用途例 |
| :--- | :--- | :---: | :---: | :--- |
| **Discrete Inputs** | 接点入力 | **Read-Only** | 1 bit | リミットスイッチ、押しボタン、アラーム検知 |
| **Coils** | コイル出力 | **Read / Write** | 1 bit | 電磁弁リレー駆動、ランプ点灯、運転/停止指示 |
| **Input Registers** | 入力レジスタ | **Read-Only** | 16 bit | ADC 計測値、温度計、電力計、電流センサー |
| **Holding Registers**| 保持レジスタ | **Read / Write** | 16 bit | 目標回転数、PID 制御パラメータ、各種設定値 |

通信コマンドは、すべてこのメモリに対する「読み出し（Read）」または「書き込み（Write）」という **CRUD 操作（Function Code）** に集約されます。

### 主要なファンクションコード一覧
- `0x01` (Read Coils): コイルの状態を 1 ビット単位で一括読み出し
- `0x03` (Read Holding Registers): 保持レジスタを 16 ビット単位で連続読み出し（最も多用される）
- `0x04` (Read Input Registers): 入力レジスタを 16 ビット単位で連続読み出し
- `0x05` (Write Single Coil): コイルを 1 点だけ ON/OFF
- `0x06` (Write Single Register): 保持レジスタを 1 点だけ書き換え
- `0x10` (Write Multiple Registers): 複数レジスタを一括書き込み

## 4. フレーム構造（ADU: Application Data Unit）

MODBUS RTU のフレームは、ヘッダー・フッターを含めて **最大 256 バイトの可変長** です。

```text
 0            1                 2 ... (N-3)                     N-2        N-1
┌────────────┬─────────────────┬───────────────────────────────┬──────────┬──────────┐
│ Slave Addr │  Function Code  │             Data              │ CRC16    │ CRC16    │
│    (1B)    │      (1B)       │         (0〜252 Bytes)        │  (LSB)   │  (MSB)   │
└────────────┴─────────────────┴───────────────────────────────┴──────────┴──────────┘
 ├── 1 Byte ─┤ ├─── 1 Byte ────┤ ├─── 可変長 (ファンクション依存) ──┤ ├─── 2 Bytes ────┤
```

### 4.1 各フィールドの仕様
- **Slave Address (1B)**: `0x00`（ブロードキャスト）または `0x01`〜`0xF7`（スレーブ個別アドレス）。
- **Function Code (1B)**: 実行する操作コード（`0x01`〜`0x7F`）。最上位ビットが `1`（`0x80`〜`0xFF`）の時は「エラー応答（Exception Response）」を意味する。
- **Data (可変長)**: レジスタ開始アドレス、読み書きするレジスタ数、実際のバイトデータなど。
- **CRC-16 (2B)**: CRC-16-IBM（多項式 `0xA001`, 初期値 `0xFFFF`）。**※注意: LSBファーストで格納される**。

### 4.2 致命的な設計の罠: 「ヘッダーに Length フィールドが存在しない」
驚くべきことに、MODBUS RTU のヘッダーには **「このパケットが合計何バイトあるか」を示す `Length` フィールドが存在しません**。

受信側（マイコン）がパケットの終わりを知る方法は以下の 2 つしかありません：
1. `Function Code` とその直後のデータを解析し、「このコマンドなら全体で $M$ バイト来るはずだ」とプロトコルの知識から逆算して受信バイト数をカウントする。
2. 後述する **「無通信時間（T3.5 タイマー）」** を計測し、データが途切れたことをもってパケット完了とみなす。

## 5. 最大の急所: 「T1.5 / T3.5 タイマー」問題

MODBUS RTU は、パケットの「開始（Start）」と「終了（End）」を特定のキャラクター（ASCII の STX/ETX など）や物理違反波形（LIN の Break、1553B の Sync）で識別しません。  
その代わりに採用したのが、**「無通信時間（サイレント・インターバル）」による時間同期** です。

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                      MODBUS RTU の 2 大時間規定                             │
│                                                                             │
│  【 T3.5 (End of Frame) 】: バスが 3.5 文字分静寂なら「フレーム終了」とみなす│
│  【 T1.5 (Character Gap) 】: 文字間隔が 1.5 文字以上空いたら「フレーム破壊」 │
└─────────────────────────────────────────────────────────────────────────────┘
```

```text
───[前の通信]───►│ 3.5文字以上静寂 │──► [Addr] [Func] [Data...Data] ──►│ 3.5文字以上静寂 │──►[次の通信]
                 │    (T3.5)      │                                    │    (T3.5)      │
                 └─ パケット開始 ─┘                                    └─ パケット終了 ─┘
                                          │ 1.5文字以内 │
                                          │   (T1.5)    │
```

### 5.1 ボーレートごとの時間換算
1 文字は通常 11 ビット（1 Start + 8 Data + 1 Parity + 1 Stop）として計算されます。

| ボーレート | 1 文字伝送時間 | T1.5（文字間タイムアウト） | T3.5（フレーム境界時間） |
| :--- | :---: | :---: | :---: |
| **9,600 bps** | $1.15\,\mathrm{ms}$ | **$1.72\,\mathrm{ms}$** | **$4.01\,\mathrm{ms}$** |
| **19,200 bps** | $0.57\,\mathrm{ms}$ | **$0.86\,\mathrm{ms}$** | **$2.01\,\mathrm{ms}$** |
| **115,200 bps** ※注 | $95.5\,\mu\mathrm{s}$ | **$750\,\mu\mathrm{s}$ (固定)** | **$1.75\,\mathrm{ms}$ (固定)** |

> ※注: 19,200 bps を超える高速域ではマイコンのタイマー精度が追いつかなくなるため、MODBUS 公式仕様書において T1.5 は $750\,\mu\mathrm{s}$、T3.5 は $1.75\,\mathrm{ms}$ の固定値とすることが推奨されています。

## 6. なぜ MODBUS RTU は現代のシステムで泣かされるのか？

専用のハードウェアタイマーを積んだ組み込み PLC 同士の通信であれば、T1.5 / T3.5 は正確に機能しました。しかし、PC や現代の環境が介在した瞬間に大惨事が発生します。

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                 MODBUS RTU が現代環境で崩壊する 3 大理由                    │
├─────────────────────────────────────────────────────────────────────────────┤
│ 1. USB シリアル変換 IC のバッファリング遅延 (CH340 / FTDI / CP2102)          │
│ 2. 非リアルタイム OS (Windows / Linux) のスケジューリング・ジッタ           │
│ 3. 市販安価 USB ドングルの Auto-DE 放電遅延との正面衝突                      │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 6.1 USB バッファリングによる「T1.5 分断事故」
USB はシリアルバイトを 1 バイトずつホストに届けるのではなく、内部の FIFO バッファに溜め、定期的なパケット（通常 1ms 周期、または最大 16ms のレイテンシタイマー）でまとめて転送します。
- **事故の構図**:
  スレーブが 10 バイトの応答を一気に送出したとしても、USB チップのタイミング次第で「前半 4 バイト」と「後半 6 バイト」が別々の USB パケットに分かれて PC に届くことがあります。
- **結果**:
  PC 側から見ると、バイト間に **数ミリ秒の隙間（T1.5 を大幅に超過）** が空いてしまい、ドライバや上位ライブラリが「パケットが途切れて壊れた」と誤判定して通信エラーになります。

### 6.2 OS ユーザー空間での「T3.5 計測不能」
Windows や Linux（非RTOS）において、ユーザー空間（Python, Node.js, ブラウザ等）のプロセスが **「$1.75\,\mathrm{ms}$ の正確な静寂」** をタイマーで計測することは極めて困難です。OS のスレッドコンテキストスイッチだけで数ミリ秒〜十数ミリ秒の遅延が平気で混入するため、パケットの切れ目が判別できなくなります。

### 6.3 Auto-DE 回路との衝突（返信が速すぎるスレーブ問題）
安価な USB-RS485 ドングルは、送信完了後に受信モードに戻るまで **約 0.5〜1.0ms の放電時間** がかかります。  
一方、MODBUS の仕様書には「スレーブが応答を開始するまでの最小待機時間（Turnaround Delay）」の明確な規定がありません。
- 高性能なマイコンを積んだスレーブが、コマンドを受信した直後（例: $0.1\,\mathrm{ms}$ 後）に超高速で返答を返してしまうと、**ドングルの受信回路がまだ復帰しておらず、返信パケットの先頭数バイト（Slave Addr や Function Code）が綺麗に消滅（化け）します**。

## 7. LM-32 と MODBUS RTU の徹底比較

MODBUS RTU が抱えるこれらの苦難を踏まえ、ADX の **LM-32** が下した設計判断の妥当性を比較検証します。

| 比較項目 | MODBUS RTU | ADX LM-32 | LM-32 の設計的勝利点 |
| :--- | :--- | :--- | :--- |
| **パケット同期・境界** | **時間同期 (T3.5 タイマー)**<br>(無通信 1.75〜4ms 待機) | **バイト同期 (`0x55 0xAD`)**<br>＋ **完全固定長 (32B)** | **USBバッファリングや OS の時間ジッタの影響を原理的にゼロ化**。<br>途中でどれだけ間が空いても、32B 揃えば確実に復元可能。 |
| **フレーム長** | 可変長 (最大 256B)<br>※ヘッダーに Length なし | **32 バイト完全固定長** | 受信バッファ長が 32B で固定確定。動的メモリ確保（malloc）やバッファ枯渇を完全排除。 |
| **Turnaround (DE 切替)** | 規定なし (機器依存)<br>※速すぎるとドングルが死ぬ | **タイムスロット内に明示予算化**<br>($T_{turn} = 0.8\sim2.0\,\mathrm{ms}$) | 安価な市販 Auto-DE ドングルでも絶対に頭切れを起こさない構造的保証。 |
| **調停と通信形態** | 1対1 ポーリングのみ<br>(スレーブ間直接通信不可) | **Master-Scheduled ＋**<br>**TOPIC Pub/Sub 傍聴** | Master が交通整理をしつつ、スレーブ同士が他ノードのパケットを直接傍聴（Sub）できる。 |
| **エラー応答** | Function Code + 0x80<br>＋ Exception Code (1B) | CRC Error 明示返信<br>(スレーブ応答シーケンス第4則) | エラー発生時に Master がタイムアウト（無応答）を待つ必要がなく、即座に検知可能。 |
| **実装メモリ (RAM)** | 受信バッファに最低 256B 必要 | **32B のみ** | ATtiny 等の SRAM 数百バイトの極小マイコンでも余裕で動作。 |

## 8. MODBUS から LM-32 が学ぶべき「優れた遺産」

MODBUS RTU を単に「時代遅れ」と切り捨てるのは早計です。45 年間現場で生き残ってきたからこそ、学ぶべき極めて秀逸な設計思想があります。

### 1. 「16ビット・レジスタ」という共通抽象化の威力
MODBUS は、相手がインバータであれ、温度計であれ、PLC であれ、すべて **「16ビットのレジスタ空間」** という単一のメタファーで表現しました。  
これにより、上位システム（SCADA や PC）は個別機器の内部構造を知らなくても「40001番のレジスタを読む」だけでデータを取得できます。
- **LM-32 への示唆**:
  LM-32 の 24 バイトペイロードに対しても、「レジスタマップ」や「パラメータブロック」としての統一的な読み書き（CRUD）トピックを用意することで、Modbus 同様の汎用性を獲得できます。

### 2. Exception Response（例外応答コード）の体系
MODBUS では、要求を処理できなかった場合に、スレーブが明示的に以下のエラーコードを返します：
- `0x01` (Illegal Function): 未対応のコマンド
- `0x02` (Illegal Data Address): 存在しないアドレス
- `0x03` (Illegal Data Value): 範囲外の値
- `0x06` (Slave Device Busy): スレーブが処理中
- **LM-32 への示唆**:
  LM-32 のスレーブ応答において、単なる CRC エラーだけでなく、「コマンド未対応」「パラメータ範囲外」「Busy」を 1 バイトで Master に返す仕組み（Status / Exception）を取り入れると、デバッグや上位制御の信頼性が飛躍的に向上します。

## 9. 結論

MODBUS RTU は、**「専用リアルタイムマイコン同士を直結する 1970 年代の環境」** においては完璧な規格でした。しかし、現代の **「USB 変換・マルチタスク OS・安価ドングル」** という現実においては、T3.5 タイマーと可変長フレームが最大の弱点となっています。

ADX の **LM-32** は、MODBUS の持つ「シンプルで枯れた信頼性」を継承しつつ、
1. **バイト同期（`0x55 0xAD`）と 32 バイト完全固定長** によって時間依存（T3.5）を根絶し、
2. **決定論的タイムスロット** によって Auto-DE 放電遅延を完全に吸収し、
3. **TOPIC Pub/Sub** によってスレーブ間の協調を実現した、

まさに **「21世紀の USB / Web 時代に最適化された MODBUS の正当進化形」** と位置づけることができます。
