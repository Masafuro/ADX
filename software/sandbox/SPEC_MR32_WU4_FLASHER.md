## 1. 今回の試作の「真の目標」（Why & What）

### 1.1 背景と原点
産業現場における HMI / 保全の理想は、**「高価な専用書き込み機や複雑な Windows 環境を一切使わず、作業員のポケットの中にあるスマホ（または PC）と、100円ショップの USB ケーブル、市販の数百円のドングルだけでファームウェア更新を完結させる」** ことである。

### 1.2 今回の試作で達成すべき「合格基準」
| 項目 | 目標仕様 | 現状の到達点 | 課題とギャップ |
| :--- | :--- | :--- | :--- |
| **① 物理接続** | スマホ / PC 直結で通信できること | **達成 (100%)**<br>Android APK 経由で USB 認識・往路開通 | なし |
| **② 往路パケット** | マイコンがパケットを受信・パースすること | **達成 (100%)**<br>Chunk 0 で白LEDトグルを確認済 | なし |
| **③ 復路パケット** | マイコンの返信パケットをホストが受信すること | **未達 (0%)**<br>タイムアウトで拾えていない | ドングルの Auto-DE 切替遅延、マイコンの返信タイミング |
| **④ 電源投入同期** | 電源抜き差し時に人間がタイミングを計らず自動同期 | **未達 (0%)**<br>手動一発勝負で失敗 | 電源待受ポーリング周期の欠落 |
| **⑤ 耐ノイズ性** | 偶発的な 1 パケット欠落で即死しない | **未達 (0%)**<br>1 回のタイムアウトで即エラー停止 | 再送制御（ARQ）の欠落 |

## 2. 現状の物理的到達点の正確な位置づけ

> [!NOTE]
> **「ある程度、通信はできているっぽい」の物理的真実**
> - 「書き込みを押すたびに白LEDがトグルする」という事実は、**往路（スマホ $\rightarrow$ Core-D）の全レイヤー（USBドライバ、ボーレート、物理配線、差動ドライバ、マイコンUART、パケットパーサー、CRC16）が 100% 整合している** ことを意味しています。
> - 壊れている箇所は一つもなく、残る課題は **「半二重（Half-Duplex）特有の時間設計（タイミングと周期）」** の一点に集約されます。

## 3. 通信開発仕様（タイミング＆プロトコル設計）

市販の安価な USB-RS485 ドングル（CH340 + MAX485 クローンの Auto-DE 回路）と、ATtiny1616 のハードウェア特性を両立させるための確定仕様を以下に定義します。

### 3.1 時間設計（Timing Specification）の確定
半二重 RS-485 において最も致命的となるパラメータを以下のように厳密に規定します。

```text
【ホスト送信】               【マイコン処理】                 【マイコン返信】
   32 Bytes                   T_guard (1.5ms)                  32 Bytes
┌─────────────┐             ┌─────────────────┐             ┌─────────────┐
│  TX パケット │             │  Auto-DE 復帰待ち│             │  ACK 返信   │
└─────────────┘             └─────────────────┘             └─────────────┘
              ▲                               ▲             ▲             ▲
              └─────── 送信完了                │             │             │
                                              └─ ドングルDE=0 │             └─ 返信完了
                                                 (受信モード)  └─ マイコン送信開始
```

| パラメータ | 記号 | 規定値 | 設計意図・根拠 |
| :--- | :--- | :--- | :--- |
| **ホスト送信時間** | $T_{tx\_host}$ | 約 2.78 ms | 115,200 bps における 32 バイト（320 ビット）の物理送信時間 |
| **返信ガード時間** | $T_{guard\_reply}$ | **1.5 ms** | **【最重要】** パケット受信後、マイコンが返信を開始するまでの待機時間。ドングルの Auto-DE 回路（RC放電）が確実に受信モード（DE=0）へ戻るのを待つ。 |
| **マイコン返信時間** | $T_{tx\_mcu}$ | 約 2.78 ms | 115,200 bps における 32 バイト（320 ビット）の物理返信時間 |
| **チャンク間インターバル** | $T_{chunk\_gap}$ | **3.0 ms** | ホストが返信を受信してから、次のチャンクを送るまでの息継ぎ時間。マイコンが受信モードへ確実に切り替わる時間を確保。 |
| **待受ポーリング周期** | $T_{poll\_interval}$ | **40 ms** | 書き込み開始前、Core-D の電源投入（起動）を自動検出するために Ping (0x10) を送る間隔。 |
| **最大リトライ回数** | $N_{retry}$ | **3 回** | 各チャンクの送受信タイムアウト時に再送を試みる回数（Stop-and-Wait ARQ）。 |
| **応答タイムアウト** | $T_{timeout}$ | **200 ms** | Android WebView の IPC 遅延（5〜30ms）を十分吸収できる待ち受け時間。 |

## 4. 通信速度（ボーレート）の仕様方針

安価なドングルの耐性に関して、以下の 2 段階方針を定めます：

1. **第 1 選択（現状維持）: 115,200 bps**
   - 上記の「$T_{guard\_reply} = 1.5\text{ms}$」および「$T_{chunk\_gap} = 3.0\text{ms}$」の時間設計を適用することで、安価ドングルでも 115,200 bps のまま安定動作可能かを検証する。
   - 理由: 12KB の転送が約 6 秒（実効 2.0 KB/s）で完走する圧倒的快感があるため。
2. **第 2 選択（安全フォールバック）: 38,400 bps または 19,200 bps**
   - もしドングルの個体差（波形の鈍り）で 115,200 bps が物理的に不安定な場合、安全確実な速度へ落とす。
   - 38,400 bps の場合: 12KB 転送は約 18 秒（実用上十分な速度）。
   - 19,200 bps の場合: 12KB 転送は約 36 秒（BR32 と同等の鉄壁の安定性）。

## 5. PWA / HTML シーケンスの改修仕様（設計方針）

次回改修で PWA（`docs/flasher/app.js`）およびマイコン側に導入すべき具体的仕様：

### ① 書き込み開始フローの自律化（Auto-Sync）
- ボタン押下後、いきなり Chunk 0 を送るのではなく、**「Stage 1: Core-D 待受ポーリング（40ms 周期で Ping 送信）」** を開始する。
- ユーザーが Core-D の電源を入れた瞬間、Ping 応答を自動検知して「接続確立！」と表示し、自動的に Stage 2（12KB 書き込み）へ移行する。
- これにより、「電源抜き差し後に手動で切断・再接続する」という不自然な運用が完全に消滅する。

### ② チャンク転送の Stop-and-Wait ARQ（再送制御）
- チャンク送信ごとに最大 3 回まで自動リトライ。
- 1 回取りこぼしても、2 回目で拾えればそのまま何事もなかったかのようにプログレスバーが進む粘り強さを実装する。

### ③ マイコン側の返信前ウェイト
- `m4_bootloader.c` のパケット処理部において、`rs485_tx_start()` の直前に `_delay_ms(1.5)` を 1 行追加する。
