> [!NOTE]
> **U5 メモ「ネジ穴が大きく見えた件」の Gerber 実測確認**  
> 出力した [unomodoki_gerber.zip](outputs/unomodoki_gerber.zip) 内の `Drill_NPTH_Through.DRL` を照合したところ、実際の CNC ドリル径は **`T02C3.17500`（`3.175 mm = 125.00 mil`）** で、Arduino UNO R3 図面（`Ø125 mil`）と `0.001 mm` の狂いもなく一致していました。2D 表示ではベタ銅クリアランス（片側 ~12 mil）と合わさって穴径が約 `150 mil` に大きく見えるうえ、UNO R3 の左上穴 `MH4` は `SCL` ヘッダから `140 mil` しか離れていないため視覚的インパクトが強く出ます。

## 3. EasyEDA Pro 4.1.105 AI API 実践ノウハウ集（M5 必須ルール 11 箇条）

今回の実戦で実際に踏み抜き、解決・実証した API 固有の挙動と運用ルールです。M5（`CORE-U rev6`）ではこれを標準規約として組み込みます。

| # | カテゴリ | 発見した罠・実測挙動 | M5 で徹底する鉄則 |
| :-: | :--- | :--- | :--- |
| **1** | **部品選定・極性** | 同じ `KT-0603*` LED シリーズでも色により `Pin1=A/K` が逆転（緑・青は `1=K, 2=A`、黄・赤は `1=A, 2=K`）。また記憶頼りの LCSC 番号は別部品に化けやすい。 | LCSC 番号の暗記入力は厳禁。必ず `LIB_Device.getByLcscIds()`＋`getAllPinsByPrimitiveId()` で **4 部品/バッチ** に分けて実測確定する（23 部品一括は 120s タイムアウト）。 |
| **2** | **回路図回転角** | `sch_PrimitiveComponent.create(..., rot=90)` は内部で `270`（時計回り）へ正規化される。要求角度を基準に `+180` 反転すると空振りする。 | 部品の向き補正時は必ず配置後の **`cur.getState_Rotation()` を実測取得** してから `(actual + 180) % 360` で回転する。 |
| **3** | **回路図 DRC** | 電源/GND フラグ直結ワイヤへ `net` 文字列を付けると `ONENETNAME` 警告。意図的 NC ピンは `CHECKFLOATPIN` 警告を出し、`check(..., false)` を `false` にする。 | 電源/GND フラグ直結ワイヤの `net` は空文字にし、信号ネットは 1 セグメントのみ `net` 指定。`check(true, false, true)` の戻り値をルール別にフィルタ検証し、NC 以外の警告・エラーを厳密に 0 件化する。 |
| **4** | **重複部品防止** | `invoke` がタイムアウトしても EasyEDA 内部で配置が継続し、リトライ時に `R10` 等の自動リネーム重複部品が発生することがある。 | 配置後は必ず **ホワイトリスト部品数アサート** と **Protel2 ネットリスト自動全数照合**（期待ネット数・全ピン一致）を実行し、余剰部品を即削除する。 |
| **5** | **U3 配置ゲート** | 配線前だからと `pcb_Drc.check` を省略すると、`J_USB` 前シェルの外形距離違反（`7.2 mil < 11.8 mil`）を見逃す。 | **U3 配置完了直後に必ず `pcb_Drc.check(true, false, true)` を実行し、`Connection Error` 以外の全カテゴリ（`Clearance` 等）が 0 件であることを自動アサート**する（[レポート](report/u3_usb_outline_clearance_report.md)）。 |
| **6** | **PNG 撮影順序** | `pcb_Drc.check()` は `userInterface=false` でもキャンバス上の全未配線パッドに黄色 `×` を一斉描画する副作用がある。 | 人間レビュー用 PNG（`getCurrentRenderedAreaImage()`）は **必ず `pcb_Drc.check()` の「前」に撮影する**（[レポート](report/u3_pad_x_markers_investigation.md)）。 |
| **7** | **ビア作成順序と最小径** | 配線を先に作って後からビアを置くと、EasyEDA Pro 4.1.105 は表裏が繋がっていても `length: 0` の未配線ラッツネストを誤報告する。また穴径 `10 mil` は標準ルール `>= 11.8 mil` に抵触する。 | **必ず `pcb_PrimitiveVia.create()` を `pcb_PrimitiveLine.create()` より先に呼ぶ**（Via-Before-Track 原則）。標準ビアは **`hole = 12 mil / dia = 22 mil`** 以上で統一する。 |
| **8** | **長穴（Slot）の扱い** | USB-C 等のフットプリント内にあるスロット／位置決め穴は無ネットの `Slot Region` 扱いとなり、同ネット（GND）トラックでも `11.8 mil` 未満に近づくと違反になる。 | USB-C 等の GND 接続は長穴・位置決めボスを避け、パッド外側方向からベタまたはクリアランス十分な経路へ逃がす。 |
| **9** | **ベタ孤立島の解決** | 2 層高密度領域では `preserveIslands=false` のベタが信号線に囲まれ孤立しやすい。当てずっぽうのビア追加は別層の線と衝突しがち。 | PCB 全線・全ビア座標を取得し、**ローカル Node で 2 層グリッド・フラッドフィル＋幾何クリアランス計算** を行ってから 100% クリアな座標にだけビア・配線を投入する（試行回数と衝突を激減できた）。 |
| **10** | **GUI/CLI 競合防止** | CLI が開いた `origin: "cli"` ウィンドウを人間が GUI 操作すると保存チャネルがロックし、`Ctrl+S` 失敗・配線グレーアウトが発生した。 | **安全な引き渡しプロトコル**：AI 作業完了後は必ず `save()` → **`session.close(destroy: true)`** で CLI ウィンドウを閉じてから、人間が通常の `origin: "user"` ウィンドウで開く。逆も同様。なお EasyEDA の `Drag Net Name` 初期設定は **`Modify Property Position (Strict)`** を採用する。 |
| **11** | **製造ファイル出力** | `getBomFile(..., 'csv')` と `getPickAndPlaceFile(..., 'csv')` は UTF-16LE（`0xff 0xfe`）で出力される。また GUI 編集後の設計ルール形式差分で `Netlist Error` が出ることがある。 | CPL は `getPickAndPlaceFile(name, 'xlsx', 'mm')`、BOM は UTF-16LE → UTF-8 自動変換を標準化。全ネット一致を確認済みなら `importChanges(undefined, true)` で配線・配置を壊さず設計ルールを同期できる。 |

## 4. サポーター提起の次世代アーキテクチャ課題（M5 へ向けた 4 つの進化）

U4・U5 のサポーター記録（[supporter_log.md](supporter_log.md)）から、単なる「AI vs 人間の作業分担」を超えた**本質的な開発パラダイム転換のヒント**が得られました。

### テーマ A：「マッス（塊）」単位の反復型（Iterative）PCB 開発フロー
> *「ポイントはやはり修正可能性だと思う。毎回全部作り直しになるのはすごく大変なので、全体をまず、絵画で言うところのいくつかのマッス（塊）に分けて、配線してレビュー、配線してレビューみたいな繰り返し型の開発方式を考えるべきかもしれない。」*

- **今回（UNOMODOKI R3）の課題**: スクリプトを一気通貫で流す構造に近く、途中の微修正や部分やり直しが重くなりやすい。
- **M5（`CORE-U rev6`）での新設計**: 基板を機能ブロック＝**5 つのマッス**に分割し、マッスごとに「配置 → 配線 → クリーン PNG 確認 → `locked: true` 固定」を反復するインクリメンタル設計を採用する：
  1. **マッス 1（メカ骨格）**: `8858` 外形・四隅 M3 穴（`Ø5.8 mm` ネジ頭キープアウト付）・`IDC 20P`・`USB-POW`・`USB-COM`
  2. **マッス 2（電源幹線＆保護）**: `USB-POW` → TVS → `TPS259470A` eFuse → `VBUS_PROT`（2A 太幅配線）→ `TPS70933` LDO
  3. **マッス 3（計測アナログ）**: `10mΩ` シャント＋`TP181A2`（ケルビン配線）＋ `VBUS_VSENSE` 分圧 → `ATtiny1616`
  4. **マッス 4（MCU ＆ バス）**: `ATtiny1616-MNR`（QFN-20-EP）⇄ `IDC 20P` バス配線
  5. **マッス 5（デバッグ＆UI）**: `USB-COM` → `USBLC6` → `CH342K`（Mode 1 完全遮断回路）＋ `LED_SYS` / `LED_MCU` ＋ 大量シルク

### テーマ B：直角配線（90°）からの卒業 ＆ GUI オートルーティング操作の撤廃
- **直角配線について**: 16MHz / 低速デジタル帯域の 2 層基板では 90° コーナーによる電気的破綻はないものの、本番の産業用・2A 電源・アナログ混載基板（`CORE-U rev6`）では酸トラップ予防・配線密度向上・美観の観点からも **45° 面取り配線** を標準にすべきです。
  - **実装案 1（AI 自作ルーター側）**: ポリライン座標列の直角頂点を自動で `d` mil（例：`15〜25 mil`）斜め 45° カットする共通ヘルパー関数をスクリプト基盤へ導入。
  - **実装案 2（EasyEDA API 自動配線の活用 — 新発見！）**: U4 終盤の `doc.api` 調査で、EasyEDA Pro 4.1.105 には以下の Beta API が実装されていることを発見しました：
    - `eda.pcb_Document.startAutoRouting()` / `autoRouting()`（EasyEDA 内蔵オートルーターの API 起動）
    - `eda.pcb_ManufactureData.getDsnFile()` ＋ 外部 FreeRouting ＋ `eda.pcb_Document.importAutoRouteSesFile()`
  - これにより、M5 では **「重要マッス（電源・アナログ・差動 USB）を AI が 45° 配線して `locked: true` 固定 → 残りの一般デジタル線を AI 自身が API 経由でオートルーティング → 表裏 GND ベタ＆DRC 0」** までを一気通貫で自動化し、**人間が GUI でオートルーティングを回すストレスをゼロにできる**可能性が高いです（M5 着手前の 15 分ミニ実験で動作確認推奨！）。

### テーマ C：フットプリント外形（Courtyard）推定 ＆ 部品クリアランス自動検証
> *「抵抗が IC と一部かなり近接している箇所がある。様々な IC のフットプリントから外形サイズを推定し、部品クリアランスチェックルールを作れるか実験しがいがありそう。」*

- **現状の盲点**: EasyEDA の標準 PCB DRC は「銅箔パッド同士」「パッド対外形」は 100% 検知できますが、**「0603 抵抗のセラミック本体と IC 樹脂パッケージの近接（手直し・リフロー検査のしにくさ）」** や **「3D コネクタの突き出し量」** は標準 DRC に引っかかりません。
- **M5 対策**:
  1. `bom_verified.json` に各パッケージの **実装ボディ寸法＋最小 Courtyard マージン**（例：`0603` = `1.6×0.8 mm + 0.5 mm`、`TQFP/QFN/SOP` = パッド外接矩形 `+ 0.6 mm`、`M3 ネジ頭` = `Ø5.8 mm`）を持たせる。
  2. U3 配置スクリプト実行時に **全 37+ 部品の Courtyard 矩形同士の交差・最小間隔を Node 側で自動計算し、違反 0 件をアサート** する（AI が機械的に「ちょうどいい余裕のある配置」を保証）。
  3. そのうえで、最終的な 3D 物理突き出し・ケーブル挿抜感・LED 視認性だけを人間が EasyEDA 3D ビューで 5 分検品する。

### テーマ D：人間フレンドリーなレビュー UX の標準化
- **生 JSON レビュー禁止**: 人間へ渡す確認物は常に「Markdown 要約表（[bom_summary.md](bom_summary.md) 等）」「DRC 前のクリーン PNG」「測定ツールチェック表」に整形する。
- **ドキュメント責務分離**: 「指示書（読む専用）」と「記録書（書く専用）」を分離する方式は非常にスムーズに機能したため、M5 でも標準テンプレートとして採用する。

## 5. ADX 本丸（M5：`CORE-U rev6`）確定分業方針：**全工程 AI 主導へ移行**

U6 サポーター確定方針（[supporter_log.md](supporter_log.md)）に基づき、M5 以降は **全 10 工程を「AI 主導」へ移行** します。人間（サポーター）の役割は GUI 手作業ではなく、**「仕様・評価基準の意思決定」「AI が自律開発しやすい専用インフラ・ツールの整備」「2D/3D 成果物の最終検品」** へ集約します。

| 設計工程 | 確定担当 | M5 での運用ルール・改善ポイント |
| :--- | :---: | :--- |
| **LCSC 部品選定・在庫/定格検証** | **AI 主導** | `-40〜+105℃` 耐熱・Basic 優先・全ピン極性を 4 部品/バッチで実測し、人間向け Markdown 表で承認を得る。 |
| **回路図の自動生成・配線** | **AI 主導** | マッス（機能ブロック）分割＋ネットラベル中心で 100% AI 生成。人間はクリーン PNG で電気意図を確認。 |
| **SCH DRC・ネットリスト監査** | **AI 主導** | 意図的 NC フィルタ＋Protel2 ネットリスト自動全数照合で 0 エラーを保証。 |

## 7. 次フェーズ確定 R&D ロードマップ（U6 サポーター提言の整理）

U6 の総括（[supporter_log.md](supporter_log.md)）で示された **「AI 主体の実用的な回路・PCB 開発環境を本格構築する」** 方針に基づき、M5（`CORE-U rev6`）着手前〜並行して取り組むべき 5 本柱を整理しました。

### 柱 1：先行研究・既存 AI 回路設計ノウハウの徹底調査（サーベイ論文・レポート作成）
- 車輪の再発明を避けるため、まず最優先で **世界の AI 回路設計・自動配置配線（AI-driven PCB Placement & Routing / LLM + EDA / トポロジカルルーター / 物理場ルーター / 強化学習・ベイズ最適化配置）** の最新研究・OSS・産業事例を網羅的に調査し、体系的なサーベイレポート（論文形式）にまとめる。

### 柱 2：3 階層「マッス」設計パイプライン ＆ フットプリント外接矩形の自動取得
1. **全体のマッス分割**（機能・電源・ノイズドメイン単位のブロック定義）
2. **マッスごとの配置エリア下書き**（フロアプランニング）
3. **マッス内の部品配置下書き**
- **技術的関門**: EasyEDA API / フットプリント定義（パッド群・シルク枠・3D モデルバウンディングボックス）から **各部品の正確な外接矩形（長径・短径・Courtyard）を汎用的に自動抽出できるか** を検証・基盤化する。

### 柱 3：次世代ルーティング理論（物理ポテンシャル場・非 45° 曲線配線・不可能性への回帰）
- **AI 事前準備 × 高度オートルーティング（物理ポテンシャル場構想）**: パッドや配線に磁石の N/S 極のような引力・斥力関係（Force-Directed / Potential-Field）を与え、パッドから出発した配線が全体の力学バランスに沿って滑らかに位置調整・回避していくアプローチや、既存トポロジカルルーターとの比較を研究する。
- **「45° ルール」自体の本質的再検討**: 人間の手配線時代の慣習である 45° 制約が電気的・製造的に本当に最適なのかを疑い、**任意角（Any-Angle）・多角形・曲線（Curved / Serpentine / Topological）配線** の方が配線長短縮・インピーダンス均一性・製造歩留まりで優れている可能性を検証する。
- **配線不可能性（Unroutability）と配置-配線協調最適化**: 部品の配置や回転角が悪いせいで物理的に解が存在しない状態（交差不可能性・ボトルネック）をどう数理検知し、**「部品の回転・再配置」へ自動フィードバックする閉ループ** を組むか設計する。

### 柱 4：GND ビア配置の理論化（電気的・機械的意味論 ＆ レビュー可能性）
- アドホックに点在する GND ビアから脱却し、**「マッス単位の GND 領域分割 → 外周シールド（ビアフェンス）＆ 内部リターンパス近傍への規則的配置」** というルールを策定する。
- 各 GND ビアに **電気的意味論**（リターン電流・EMI 遮蔽・熱拡散）、**機械的意味論**（基板強度・放熱・製造クリアランス）、および **レビュー可能性**（なぜそこにビアがあるか人間と AI の双方が一目で検証できる構造化メタデータ／可視化）を与える。

### 柱 5：専用 Windows 実行基盤（LAN 内 Omnivoice GPU マシン）への EasyEDA 環境移設
- 開発者の作業用ノート PC 上で EasyEDA Pro を同居させると、GUI 競合・作業中断・非・常駐運用コストが発生する。
- LAN 内にすでに稼働している **Podcast 生成用の Omnivoice GPU Windows マシン** へ EasyEDA Pro ＋ `start_easyeda_bridge.bat` を専用実行ノードとして再構築し、AI が開発者の手元環境を一切邪魔せずに高速・自律的に試行錯誤できる開発インフラを確立する。
