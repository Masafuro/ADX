# 実験条件に関する基礎設計 (Experimental Conditions Base Design)
**― MR32 先行開発における Flash メモリ区画および安全運用規程 ―**

## 1. 策定の背景と目的

ADX 基幹フィールドネットワーク「MR32」の先行研究開発（テストベンチ: ADX Core-D / ATtiny1616）において、以下の開発フェーズ特有の現実的な要件が存在する：

1. **実験用ブートローダーのサイズ制約**:
   先行開発フェーズ（M3〜M4）では、詳細なエラー判定、生パケット解析、テレメトリ出力、および可視化ロジックを搭載するため、ファームウェアバイナリが **1.5KB〜2KB 程度** となり、即座に極小化（<1024B）することはできない。
2. **Flash 物理書き込みテストの安全な遂行**:
   その状態で、マイコン自身が自律的に Flash メモリを消去・書き換える（Self-Programming）実機実証を安全に行う必要がある。
3. **M3 における教訓（自爆現象の再発防止）**:
   M3 の初期実験において、保護境界を「Page 16 (0x0400 = 1024B)」と過小評価したまま「Page 20 (0x0500)」に書き込みを実行した結果、約 1,965B あったファームウェア自身のコード空間のど真ん中を物理消去・上書きして自爆（CPU 暴走）に至る事象が確認された。

本資料は、これらの教訓を踏まえ、**先行実験フェーズにおいて二度と自爆を起こさず、かつ十分なアプリケーション空間を確保するための Flash メモリ区画設計およびハードウェア運用規程** を基礎設計として明確に定義する。

## 2. Flash メモリ区画設計（実験フェーズ用 4KB / 12KB 分割）

ATtiny1616 の 16KB Flash（全 256 ページ / 1 ページ = 64 Bytes）を以下のように分割定義する。

```text
 物理アドレス        ページ番号       区画名                 役割・安全設計
0x0000 ────────── Page 0  ┌─────────────────────────┐
                          │                         │ ★ 自爆防止ハードロック領域 (4,096 B / 4KB)
                          │  実験用ブートローダー   │ ・実験ファーム (約 2KB) に対して安全マージン 100%
                          │  (Bootloader Space)     │ ・ファームウェア内部で Page < 64 を完全拒絶 (0x03)
                          │                         │ ・デバッグコード・テレメトリの自由な追加を許容
0x0FFF ────────── Page 63 └─────────────────────────┘
0x1000 ────────── Page 64 ┌─────────────────────────┐ ◄─── ★ M3 実験ターゲット: Page 64 (0x1000)
                          │                         │
                          │  アプリケーション領域   │ ★ 自由書き換え可能領域 (12,288 B / 12KB / 192P)
                          │  (Application Space)    │ ・M3: 単一ページ物理書き込み・Bit-for-Bit 照合
                          │                         │ ・M4: ユーザーアプリ (LED点滅等) のフル OTW 空間
                          │                         │
0x3FFF ────────── Page 255└─────────────────────────┘
```

### 2.1 区画パラメータ仕様表

| 項目 | 設定値 | 物理アドレス空間 | 属性・制約 |
|:---|:---|:---|:---|
| **MCU Flash 総容量** | 16,384 Bytes (256 ページ) | `0x0000` 〜 `0x3FFF` | 64 Bytes / ページ |
| **実験ブートローダー区画** | **Page 0 〜 63 (64 ページ / 4,096 B)** | **`0x0000` 〜 `0x0FFF`** | **書込完全禁止 (LOCKED)**<br>アクセス時は `STATUS_ERR_PARAM (0x03)` で即座に拒絶 |
| **アプリケーション区画** | **Page 64 〜 255 (192 ページ / 12,288 B)** | **`0x1000` 〜 `0x3FFF`** | **書込許可 (WRITABLE)**<br>OTW 書き換えおよび消去を完全許容 |
| **M3 物理書込テスト対象** | **Page 64 (先頭 64 Bytes)** | **`0x1000` 〜 `0x103F`** | 自爆リスクゼロの安全な実証ポイント |

### 2.2 本設計の採用理由

1. **絶対自爆防止（安全マージン 100%）**:
   現在の実験用ファームウェア（約 1,965 Bytes）に対し、4,096 Bytes（Page 64）の境界を設けることで、約 2 倍以上のバッファを確保。今後テレメトリや新コマンドを拡張しても自爆領域を侵犯しない。
2. **キリの良い 16 進境界**:
   物理アドレス `0x1000`（4,096）というキリの良い境界となり、デバッガやホストスクリプトでの視認性・管理性が向上する。
3. **広大な 12KB アプリ空間**:
   将来の Milestone 4（16KB フル OTW）において、LED 点滅、UART 通信、センサ制御などの本格的なユーザーアプリケーションを実機検証するのに十分すぎる空間（12KB = 192 ページ）が残る。
4. **本番（M5）へのスムーズな移行**:
   最終マイルストーン（M5）においてコード極小化（<1024B）を達成した段階で、境界を `Page 16 (0x0400 = 1KB)` に引き下げ、本番用の 15KB アプリ空間へシームレスに拡張する。

## 3. NVMCTRL（Flash 自己書き込み）安全運用規程

Flash メモリの自己プログラミング（Self-Programming）を安全に行うため、ファームウェア実装において以下の規程を遵守する。

### 3.1 NVM コマンドレジスタの明示的クリーンアップ
`NVMCTRL.CTRLA` に `PAGEERASEWRITE` などのコマンドを発行した後は、物理消去・書き込み完了待ち（`FBUSY` / `EEBUSY` が 0 になるまで）を行った直後に、**必ず `NVMCTRL_CMD_NONE_gc`（コマンドクリア）を発行して待機状態に戻す**。
これを怠ると、以降の通常の Flash 読み出しアクセスが意図しない NVM 操作として誤認される原因となる。

```c
// 規程: NVM 書き込みシーケンスの実装標準
__attribute__((noinline))
static void nvm_commit_page_hw(uint16_t page_idx) {
    uint16_t page_addr = page_idx << 6;
    uint8_t *dest = (uint8_t *)(MAPPED_PROGMEM_START + page_addr);

    // 1. ページバッファへのデータロード
    for (uint8_t i = 0; i < FLASH_PAGE_SIZE; i++) {
        *(dest++) = sram_page_buffer[i];
    }

    // 2. ハードウェア消去・書き込みトリガー
    _PROTECTED_WRITE_SPM(NVMCTRL.CTRLA, NVMCTRL_CMD_PAGEERASEWRITE_gc);

    // 3. ハードウェア完了待ち (約 2.5ms CPU ストール)
    while (NVMCTRL.STATUS & (NVMCTRL_FBUSY_bm | NVMCTRL_EEBUSY_bm))
        ;

    // 4. 【必須規程】NVMCTRL を待機状態 (NONE) に完全復帰
    _PROTECTED_WRITE_SPM(NVMCTRL.CTRLA, NVMCTRL_CMD_NONE_gc);
}
```

### 3.2 自爆防止ガード境界チェック
書き込み要求（`CMD_BOOT_WRITE_CHUNK`）を受信した際、要求ページ番号（`req_page`）が `APP_START_PAGE`（Page 64）未満、または `FLASH_TOTAL_PAGES`（256）以上である場合は、いかなるバッファ操作・NVM 操作も行わず、即座に `MR32_STATUS_ERR_PARAM (0x03)` を返信して処理を中断する。

```c
#define APP_START_PAGE      64   // Page 64 = 0x1000 (実験フェーズ保護境界)
#define FLASH_TOTAL_PAGES   256

if (req_page < APP_START_PAGE || req_page >= FLASH_TOTAL_PAGES) {
    // 自爆防止ガード発動: 書込拒絶
    tx_buf[6] = MR32_STATUS_ERR_PARAM; // 0x03
    ...
}
```

## 4. ハードウェア・通信動作基準値

先行実験において使用する通信およびクロックの基準値は以下の通りとする。

| パラメータ | 基準値 | 根拠・設定 |
|:---|:---|:---|
| **MCU メインクロック** | **20.0 MHz** | 内部高精度オシレータ（`_PROTECTED_WRITE(CLKCTRL.MCLKCTRLB, 0);`） |
| **RS-485 ボーレート** | **115,200 bps (8N1)** | `USART0.BAUD = 694`（誤差 0.16% 以内） |
| **半二重ガード時間 ($T_{guard}$)** | **$\ge 150\,\mathrm{\mu s}$** | 送信完了（`TXCIF`）から DE//RE 受信復帰までの待機時間（実測 160μs） |
| **MR32 フレーム長** | **32 Bytes 固定長** | ヘッダ 6B + ペイロード 24B + CRC16 2B |
| **同期・マジックバイト** | **`0x55 0xAD`** | SYNC (`0x55`) + MAGIC (`0xAD`) |

## 5. 開発・実験前安全チェックリスト

新しいマイルストーンや実験ファームウェアをビルド・実行する際は、必ず以下のチェックを実施する：

- [ ] **バイナリサイズ確認**: `avr-size` の `text` セクションが **4,096 Bytes（Page 64）未満** であること。
- [ ] **保護境界マクロ確認**: ファームウェア内部の `APP_START_PAGE` が **`64`** に設定されていること。
- [ ] **ホストスクリプト確認**: テスト対象ページ引数（`--page`）が **`64` 以上**（推奨: `64`）であること。
- [ ] **NVM クリーンアップ確認**: Flash コミット処理の末尾に `NVMCTRL_CMD_NONE_gc` が存在すること。
