## 2. パケット通信プロトコル仕様 (8 バイト固定フレーム)

USB ドングルの送信ジッターや OS バッファリングによるパケット分断誤認を防ぐため、**8 バイト固定長フレーム** を採用した。

```
 [PC -> Core-D リクエストパケット]
 +------+------+------+-------+-------+-------+----------+------+
 | STX  | SEQ  | CMD  | DATA0 | DATA1 | DATA2 | CHECKSUM | ETX  |
 | 0x02 | 0-FF | code | 8-bit | 8-bit | 8-bit |  8-bit   | 0x03 |
 +------+------+------+-------+-------+-------+----------+------+
   ※ CHECKSUM = (STX + SEQ + CMD + DATA0 + DATA1 + DATA2) & 0xFF

 [Core-D -> PC レスポンスパケット]
 +------+------+------+-------+-------+-------+----------+------+
 | STX  | SEQ  | RESP | DATA0 | DATA1 | DATA2 | CHECKSUM | ETX  |
 | 0x02 | 0-FF | ACK  | 8-bit | 8-bit | 8-bit |  8-bit   | 0x03 |
 +------+------+------+-------+-------+-------+----------+------+
```

### コマンド仕様
1. **`CMD_PING` (`0x01`, 奇数回試行)**:
   - 疎通確認コマンド。
   - スレーブは `RESP_ACK (0x06)` とともに、`DATA1 = 0xAA`、`DATA2 = 累計受信パケット数` を返送。
2. **`CMD_ECHO` (`0x02`, 偶数回試行)**:
   - データ完全性テスト。
   - PC が毎回ランダムに生成した 3 バイト（`DATA0..2`）を送信し、スレーブがそのままエコーバック返信。PC 側で 1 バイト単位で完全一致を検証。

## 3. 確立されたハードウェア・ファームウェア制御仕様

### (1) ピンアサインと電気的制御
- **PA1**: USART0 TXD (Alternate Pin)
- **PA2**: USART0 RXD (Alternate Pin)
- **PA4**: RS-485 DE (Driver Enable, Active HIGH via `VPORTA`)
- **PA7**: RS-485 /RE (Receiver Enable, Active LOW via `VPORTA`)
- **PB2**: オンボード赤色 LED (パケット処理中点灯)
- **PB4**: CH342K デバッグテレメトリ (Soft-UART TX)

### (2) トランシーバ送受信切替タイミング（黄金比）
```c
static inline void set_tx_mode(void) {
  VPORTA.OUT |= (1 << 4) | (1 << 7); // DE=1, /RE=1 (送信イネーブル、自局レシーバ無効化)
  _delay_loop_2(830);                // ~1ms トランシーバ安定化遅延
}

static inline void set_rx_mode(void) {
  while (!(USART0.STATUS & USART_TXCIF_bm)); // 送信完了（ストップビット完了）まで待機
  USART0.STATUS = USART_TXCIF_bm;            // フラグクリア
  _delay_loop_2(830);                        // ~1ms バス解放遅延
  VPORTA.OUT &= ~((1 << 4) | (1 << 7));      // DE=0, /RE=0 (受信イネーブル)
}
```

## 4. なぜ当初うまくいかなかったのか？（全トラブル要因の総括解明）

プロジェクト初期から今回の 100% 達成に至るまでに遭遇したトラブルの因果関係は、**全く独立した 4 つの要因** に明確に分類される。

| 要因 | 発生段階 | 事象・症状 | 動かぬ真相 (物理的メカニズム) | 解決策 |
| :--- | :--- | :--- | :--- | :--- |
| **要因 1: ハードピン誤り (真因)** | 初期〜調査中 | 電源投入直後だけ数回通信でき、その後二度と応答しなくなる | **DE (PA4) が未初期化 (Hi-Z) で浮いていた**。<br>電源投入直後の浮遊寄生容量チャージで数秒間たまたま HIGH になり、放電して LOW に落ちた瞬間に送信不能になっていた。 | PA4 (DE) と PA7 (/RE) を明示駆動 |
| **要因 2: ボーレートマージン** | 初期テスト (19200 bps) | パケット化け、フレーミングエラー | 19200 bps では 1 ビット幅が 52.1 µs しかなく、内蔵オシレータの誤差や USB ドングルのジッター許容マージンが狭すぎた。 | **9,600 bps (104.2 µs)** をベースラインに採用 |
| **要因 3: LIN Break ジッター** | LINAUTO 実験 | ブレーク同期が安定しない | Windows の USB シリアル（FTDI/CH340）からミリ秒未満の正確な Break 信号（1042 µs）を生成するのが困難で、同期ジッターが発生していた。 | Break 信号に依存しない通常 UART フレーム（STX/ETX）を採用 |
| **要因 4: 観測問題 (Heisenbug)** | パケットベンチ第1回 (86.7%) | 試行 9, 20 で TIMEOUT、`Bad ETX` | **COM21 の Soft-UART 出力が CPU を 50ms 占有**。<br>48 文字の `[IDLE 9600]` 送出中に RS-485 パケット（8.3ms）が到着し、ハードウェア RX FIFO（2バイト）が溢れて先頭バイトをドロップしていた。 | **RS-485 応答返信を最優先実行**、通信中の IDLE 出力を完全抑止 |

> **【重要な結論】**:
> ユーザーの雑感にある通り、**「初期の不安定さ（数回で死ぬ）」はソフトウェアシリアルとは無関係** であり、**DE ピン（PA4）の浮遊電荷放電** と **19200 bps / LIN Break のタイミングマージン不足** が原因でした。
> 一方、**「今回のベンチマーク第1回の 4 回の失敗」** は、デバッグ用に導入した **Soft-UART のビジーループ占有（観測問題）** によるものでした。
> 双方を完全に切り分けて対処したことで、今回の 100.0% PASS（ジッター 0.88ms）が達成されました。
