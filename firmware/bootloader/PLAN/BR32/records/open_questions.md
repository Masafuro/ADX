# BR32 開発における未解明現象・研究課題メモ (Open Questions & Deep-Dive Archive)

本ドキュメントは、BR32 プロトコルおよびサンドボックス実験（WU-0〜WU-4）において観測された、**「直感と反する挙動」「未解明の物理・OS層の謎」** を切り離して保管し、将来の詳細分析や論文・知見蓄積の資産とするためのアーカイブです。

---

## 課題 1: 長周期ポーリング（> 300ms）における系統的ジッター悪化と配線長依存性の謎

### 1. 観測された現象 (Observation Facts)
WU-0 の「最適インターバル検査くん（`--optimize`）」を用いて、ポーリング周期を 80ms から 400ms までスイープ測定した際、以下の現象が確実に再現された：

1. **短〜中周期（100ms 〜 200ms）**:
   - ジッター $\sigma = 0.34 \sim 0.38\,\text{ms}$、変動幅 Range = $1.3 \sim 1.8\,\text{ms}$。
   - 極めて高い安定性と低ジッタープラトーを形成。
2. **長周期（300ms 〜 380ms）**:
   - **10cm 直結配線**: 320ms で $\sigma = 0.81\,\text{ms}$、380ms で $\sigma = 0.62\,\text{ms}$ と局所的な悪化。
   - **50cm（25cm+25cm WAGO中継）配線**:
     - `340.0 ms`: $\sigma = 0.75\,\text{ms}$ / Range: $3.19\,\text{ms}$
     - `360.0 ms`: $\sigma = 0.65\,\text{ms}$ / Range: $3.99\,\text{ms}$（約 4ms に拡大）
     - `380.0 ms`: $\sigma = 0.76\,\text{ms}$ / Range: $3.48\,\text{ms}$
     - **340ms〜380ms の 40ms 幅にわたるブロック全体で、ジッターが 2 倍以上に系統的・安定的に悪化** した。

「通信間隔を広げれば広げるほど、バスや処理に余裕ができて安定するはず」という直感に反し、**300ms を超えると確実に悪化する**。

---

### 2. 現状考えられる 3 大仮説 (Working Hypotheses)

#### 仮説 A: USB ドングル / ホストコントローラの「省電力モード（サスペンド移行準備）」
* USB-シリアル変換チップ（CH340/FTDI/CP210x など）や Windows の USB xHCI ホストコントローラには、通信がない無信号期間が一定時間（約 250ms〜300ms）続くと、内部クロックゲーティングや省電力サスペンド待機に入る仕様がある。
* 160ms〜200ms では省電力タイマーが常にリセットされ続けるが、340ms〜380ms では省電力モードに落ちかけ、次回の送信トリガー時に「復帰ウェイクアップ遅延（1〜3ms の揺らぎ）」が偶発的に乗る。

#### 仮説 B: 線路の長時間アイドル（Hi-Z）放置による電荷抜けと過渡立ち下がりエッジ揺らぎ
* 終端抵抗（$60\,\Omega$ 並列）が入っているため、無送信アイドル時間が 300ms を超えると、線路の浮遊容量や WAGO 接点の寄生容量から電荷が完全に抜けきる。
* この「完全放電・コモンモード浮遊」状態から、急激に強い LOW 駆動（Half-Baud の Break）を叩き込んだ際、SP485EEN のレシーバコンパレータ入力における過渡応答の立ち下がりエッジがわずかに揺らぎ、LINAUTO の Break 検出幅判定に微小な時間差を生じさせている。

#### 仮説 C: Windows OS スレッドの「休眠深度」
* Windows スケジューラは、300ms 以上スリープしているスレッドを「非アクティブ」とみなしてワーキングセットや CPU キャッシュから追い出す傾向がある。
* タイマー起床時のコンテキストスイッチ遅延が 1〜2 タイムスライス分（約 15ms の断片）乗ることで、PC 側の送信時刻そのものが揺れている。

---

### 3. BR32 プロトコルにおける暫定設計方針（実用解）
* 上記の謎の完全解明を待たずとも、実運用においては **最も安定でジッターが最小（$\sigma \le 0.38\,\text{ms}$）となる「160ms 〜 200ms（約 5〜6 Hz）」を標準運用周期として採用** することで、この悪化領域を完全に回避可能。
* したがって、現行開発は「200ms 周期」を前提として次のステップ（WU-1、および本番ブートローダー）へ進む。
