
# 産業用フィールドネットワーク DROP-Bus 仕様書：概念としてのMediatorと開発者の設計領域

**DROP-Bus** (**D**eterministic **R**elay with **O**ptional-mediator & **P**assive-failsafe Bus) において、通信プロトコルが提供するのは「物理層でのバトンリレー」と「受動的フェイルセーフ」、および「調停（Mediation）の作法」のみである。

本仕様では、通信プロトコルから再送管理やトポロジー束縛を排除し、**「メカニズム（手段）」と「ポリシー（運用・設計裁量）」を完全に分離**している。本稿では、論理概念としてのMediatorの定義と、システム開発者に委ねられる設計領域について規定する。

---

## 1. 「メカニズムとポリシーの分離」という基本哲学

従来のフィールドバス（CAN、LIN、各種トークンパッシング等）は、プロトコル層が自動再送やバックオフ制御をブラックボックスとして内包していた。この構造は開発者の手間を省く反面、周期ジッターの隠蔽を招き、最悪実行時間（WCET）の見積もりを困難にしていた。

DROP-Bus はこの責務を意図的に切り分ける。

* **プロトコルの責務（メカニズム）:**
  * 正しいバトンの受け渡し手順（LINAUTO同期 ＋ 固定長フレーム）
  * バトンが落ちた時の受動的停止（タイマー満了による全ノード一斉STO）
  * バス調停および再点火のための物理層シグナル規定
* **システム開発者の裁量（ポリシー）:**
  * Mediatorの物理的な配置（外付け、内包、あるいは非配置）
  * 再送の有無、許容回数、および介入タイミングの決定
  * システム全体のタイムバジェット（許容ジッター）の統制

---

## 2. 概念（論理ロール）としての Mediator

DROP-Bus における Mediator は、**「特定の物理基板」を指す用語ではない。**
Mediator とは、**「落ちたバトンを拾い直す、またはバスの秩序を書き換える権能を持った『論理的な役割（Role）』」** である。

```text
【形態1: 外付けアタッチメント型】
[Node 1] ─── [Node 2] ─── [Node 3] ─── (RS-485) ─── [ Dedicated Mediator ]
※ 末端は純粋な単一SKU。保守・診断・上位連携用として別基板を追加する。

【形態2: ノード内包型（Co-located Mediator）】
[Node 1 (Runner + Mediator)] ─── [Node 2] ─── [Node 3]
※ 最も電源や処理能力に余裕のあるNode 1のファームウェア内に調停ロジックを同居させる。

【形態3: 局所調停型（Local Mediator）】
[Node 1] ─── [Node 2] ───(ノイズ過酷区間)─── [Node 3 (局所リトライ機能保有)]
※ 特定の通信困難区間に対してのみ、局所的な再送権限を与える。

【形態4: 完全マスターレス型（No Mediator）】
[Node 1] ─── [Node 2] ─── [Node 3]
※ 最安・最軽量構成。ドロップ発生時は全系が潔く停止し、外部再投入まで待機。

```
プロトコルは「Mediatorの介入手順（シグナルのフォーマットと物理的作法）」のみを定義し、**「それを誰が・どこで・どのような条件で執行するか」については一切規定しない。**

### 3.2 現場環境に応じた可用性レベルの選定
| システム要件 | Mediator 実装ポリシー | 安全停止と継続のバランス |
|---|---|---|
| **超高安全性・同期重視**

| **高可用性・環境耐性重視**

(モジュール交換型装置) | **保守ツール型Mediator**（着脱式ドングル） | 稼働中のバスに意図的衝突（Break）を起こして停止させ、構成テーブルを書き換えて再点火。 |
## 4. プロトコルが規定する調停メカニズム (Mediation Mechanism)
Mediator ロールを実行する主体は、以下の共通プロトコル作法に従う。
### 4.1 意図的衝突による強制停止（Forced Collision）
稼働中のリレーに割り込む場合、Mediator はバスへ規定長以上のドミナントパルス（Break信号）を直接送出する。
 * 送信中ノードはローカルループバック不一致により即座に送信を中止する。
 * 受信中ノードはCRC不一致またはフレーミング異常によりパケットを破棄する。
 * 全ノードが受動的安全待機（沈黙）状態へと遷移する。
### 4.2 再点火フレーム（Re-Ignition Frame）
バスの静寂（無音時間 > T_{\text{timeout}}）を検知した Mediator は、正規の物理同期ヘッダを伴う再点火フレームを送出する。
```text
[ Break Field ] ──> [ Sync (0x55) ] ──> [ TARGET_ID = X ] ──> [ SENDER_ID = MEDIATOR ] ...

```
指定された Node X は、これが直前の走者からのバトンか、Mediator からの再点火パケットかを区別することなく、自身の TARGET_ID == MY_ID を検知して通常リレーを再開する。末端ノード側の受信ロジックには、いかなる例外コードも追加されない。
## 5. 本設計がもたらす優位性
 1. **ブラックボックスの完全排除:**
   「いつの間にか裏で再送が走り、制御ループが遅延していた」という組込み特有の不具合が原理的に生じない。
 2. **規格認証（IEC 61508 / ISO 13849）の説明性:**
   プロトコル自体に不確定要素（自律的な再送・バックオフ）が存在しないため、安全機能のFMEA（故障モード影響解析）および最悪時間見積もりの説明性が極めて高い。
 3. **ライフサイクルを通じた拡張性:**
   末端ノードのコードベース（単一SKU）を一切汚すことなく、同一のハードウェア資産のまま、量産機の最小構成からハイエンドな診断機能付きシステムまで自在にスケールさせることができる。
