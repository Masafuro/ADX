
# 産業用フィールドネットワーク DROP-Bus 仕様考察：データフレーム設計

**DROP-Bus** (**D**eterministic **R**elay with **O**ptional-mediator & **P**assive-failsafe Bus) は、バトン（発話権）の受け渡しと同時に各ノードのデータ伝送を1フレームで完結させる自律分散アーキテクチャを持つ。

本稿では、車載LINの制約（最大8バイト）を超越した「可変長・大容量ペイロード」の妥当性を検証し、決定論的制御と受動的フェイルセーフを両立させるデータフレーム構造について考察・規定する。

---

## 1. LIN対比における大容量化の妥当性

LIN（Local Interconnect Network）は 19.2 kbps 以下の低速通信と数バイトの電装制御（スイッチ、ドアミラー等）を前提として策定されたため、ペイロード長が最大8バイトに制限されている。

一方、DROP-Bus が大容量ペイロードを安全に扱える工学的根拠は以下の通りである。

1. **物理層（RS-485）の高速性:**  
   RS-485 トランシーバの採用により、実効レートは 115.2 kbps 〜 数 Mbps まで引き上げ可能であり、パケットサイズ拡大に伴う時間占有のオーバーヘッドを十分に吸収できる。
2. **短期周波数安定性に基づくクロックレス成立性:**  
   各ノードはフレーム先頭の `LINAUTO`（Break + `0x55`）によって受信ごとにボーレートを校正する。ATtiny1616等の内蔵RC発振器は、1フレームの伝送時間（数ミリ秒）内であれば熱ドリフトや電圧変動の影響を無視できるほど高い短期安定性を有する。したがって、数十バイトに及ぶパケットであってもビットサンプリング位置の破綻は生じない。
3. **1周1発話の伝送効率:**  
   DROP-Bus では1周期中に各ノードへ巡ってくる発話権は1回のみである。サーボの位置指令・トルクデータ・多点I/O・ステータスフラグ等を1回のバトンパスで同時に吐き出すためには、16〜64バイト程度のフレーム容量が極めて実用的となる。

---

## 2. 改訂フレームフォーマット仕様

プロトコル層として可変長（最大64バイト）をサポートし、誤り検出能力を高めるため CRC-16 を採用する。

```text
|<--- 物理同期ヘッダ --->|<------------------------- 論理フレーム ------------------------->|
+---------+------+-------+-----+-----------+-----------+------------------------+---------+
|  BREAK  | DEL  | SYNC  | LEN | TARGET_ID | SENDER_ID |   PAYLOAD (0..N Byte)  | CRC-16  |
+---------+------+-------+-----+-----------+-----------+------------------------+---------+
  >=13bit   1bit    1B     1B       1B          1B           可変 (最大64B)        2B

```
### 各フィールドの定義
| フィールド | バイト長 | 値 / 範囲 | 説明 |
|---|---|---|---|
| **BREAK** | \ge 13 bit | Dominant (0) | ハードウェアLINAUTOトリガー用の連続Lowパルス |
| **DEL** | \ge 1 bit | Recessive (1) | ブレーク・デリミタ（立ち上がりマージン） |
| **SYNC** | 1 Byte | 0x55 | オートボーレート計測用の交番ビットパターン |
| **LEN** | 1 Byte | 0x00 〜 0x40 | 後続する PAYLOAD のバイト長 N（最大64バイト） |
| **TARGET_ID** | 1 Byte | 0x00 〜 0xFE | バトンを渡す相手ノードのID（NEXT_ID） |
| **SENDER_ID** | 1 Byte | 0x00 〜 0xFE | 現在発話している自機ノードのID（MY_ID） |
| **PAYLOAD** | N Byte | 任意 | 制御データ、入出力情報、センサー値、ログデータ |
| **CRC-16** | 2 Byte | 計算値 | LEN から PAYLOAD 末尾までを対象とする誤り検出コード |
## 3. 「プロトコルの可変性」と「システムの決定論性」の統合
本プロトコルは可変長フレームのメカニズムを提供するが、システム開発者は自身の要件に応じて「柔軟性」と「完全な決定論」のどちらを採るかを設計（ポリシー）として確定させる。
```text
【アプローチA: 完全固定長運用（厳密なハードリアルタイム）】
全ノードのペイロード長を設計時に固定（例: 全員32バイト）
  │
  ├── 実行時のフレーム長変動がゼロ（ジッター = 0）
  └── サイクルタイムおよびフェイルセーフ監視タイマーが一意に確定

【アプローチB: 最大長拘束型・可変長運用（帯域最適化）】
各ノードは必要最小限のデータ長で送信（LENを動的に変更）
  │
  ├── 最悪実行時間（WCET）を「各ノードの設計上の最大長」から算出
  └── 安全停止タイマーのタイムアウト値を WCET に基づいてマージン設計

```
### 最悪実行時間（WCET）の算定モデル
ノード i のペイロード長を L_i、ボーレートを B、1バイト送信に必要なビット数を b_{\text{byte}}（スタート+データ8+ストップ=10bit）、物理ヘッダ時間を T_{\text{header}}、送受信切替ギャップを T_{\text{gap}} としたとき、1ノードのフレーム送信時間 T_{\text{node}}(i) は以下となる。
システム全体の最悪周期 T_{\text{cycle\_max}} は、全ノードが許容最大長 L_{\max}(i) を送信した時間として厳密に数式化できる。
## 4. 小型MCU（ATtiny1616）における実装上の防御機構
大容量・可変長化を極小MCUリソース上で安全に実装するため、以下の防御ロジックをステートマシンに組み込む。
### 4.1 LENの不正値ガード（バッファオーバーラン防御）
ノイズによって LEN バイトがビット化けを起こした場合、SRAM領域の破壊を防ぐため、受信直後に上限クリップを行う。
```c
#define MAX_PAYLOAD_SIZE 64

void on_len_received(uint8_t len) {
    if (len > MAX_PAYLOAD_SIZE) {
        // プロトコル違反・ノイズとみなし即座にパケット破棄
        // バトンを落とし、パッシブ・フェイルセーフ（タイマー満了）へ誘導
        abort_rx_and_wait_silence();
    } else {
        expected_bytes = len + 2; // PAYLOAD(len) + CRC(2B)
    }
}

```
### 4.2 CRC-16の選定
データ長が最大64バイトへ拡大することに伴い、バーストノイズ耐性を担保するため CRC-16-CCITT（多項式: x^{16} + x^{12} + x^5 + 1、初期値: 0xFFFF）を採用する。8バイト制限のLINで用いられるCRC-8に比べ、産業用インバータやアクチュエータ由来の誘導ノイズに対する誤検出見逃し率を極限まで低減させる。
## 5. まとめ
 * DROP-Bus のデータフレームは、LINの物理層技術（LINAUTO）を借用しつつも、**RS-485の伝送能力をフルに活かした大容量（最大64バイト）・可変長仕様**を採用する。
 * 「プロトコル側で最大長と同期手段を担保し、実際の長さの確定やジッター管理はシステム設計者が統制する」という思想により、**大容量データ伝送の実用性と、ミリ秒単位の完全な決定論的制御の双方が矛盾なく両立**する。
