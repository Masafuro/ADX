
# 産業用フィールドネットワーク DROP-Bus 仕様書：用語と基本設計

**DROP-Bus** (**D**eterministic **R**elay with **O**ptional-mediator & **P**assive-failsafe Bus) は、極限の低コスト化（完全水晶レス・単一SKU）と厳格な決定論性、および受動的フェイルセーフ（沈黙＝安全）を両立させるために策定された、RS-485半二重通信向けの分散制御プロトコルである。

---

## 1. コア用語の定義 (Terminology)

DROP-Bus では従来の「Master / Slave（支配 / 従属）」という概念を全廃し、対等な自律分散モデルを採用する。

| 用語 | 英語表記 | 定義と役割 |
| :--- | :--- | :--- |
| **ノード** | Node | ネットワークの基本構成員。同一ファームウェア（単一SKU）で動作し、自立的にバトン（発話権）をリレーする。異常時は自律復旧を試みず、即座に出力を遮断して沈黙する。 |
| **メディエーター** | Mediator | システムに任意で追加可能な**調停者（オプション機器）**。平常時は通信に介入せずログを収集し、バトンが落ちた場合や保守・ホットスワップ時のみ物理層介入を行い、再点火・調停を担当する。 |
| **バトン** | Baton | 各フレームに含まれる「次に発話すべきノードの指定権（`TARGET_ID`）」。これを受け取ったノードのみが送信を許可される。 |
| **ドロップ** | Drop | 通信エラー、未応答、ノード脱落、またはメディエーターの物理衝突によってバトンが失われ、バスが静寂に包まれる現象。 |
| **パッシブ・フェイルセーフ** | Passive Fail-Safe | バトンドロップ発生時、全ノードが再送やスキップを一切行わず、ハードウェアタイマー満了により同期して安全停止（Safe Torque Off）する安全機構。 |

---

## 2. 物理層およびクロックレス同期設計 (Physical Layer & Synchronization)

### 2.1 完全水晶レス設計（Crystal-less Operation）
各ノードは外部水晶振動子を搭載せず、MCU（ATtiny1616等）の内蔵RC発振器のみで動作する。クロックの長期ドリフトや温度特性の個体差は、フレームごとの物理同期によって完全に吸収する。

### 2.2 LINAUTO同期メカニズム
UART通信には、車載規格LINに準拠した2段階のハードウェアオートボーレート（LINAUTO）を採用する。

```text
[バス物理波形]
       |<--- Break Field --->| Delimiter |<----- Sync Byte ----->|
TX: ───┐                     ┌───────────┐ ┌─┐ ┌─┐ ┌─┐ ┌─┐ ┌─────┴─[ TARGET_ID ]──...
       └─────────────────────┘           └─┘ └─┘ └─┘ └─┘ └─┘
       |<--- 13~14 bit 0 --->| (1 bit 1) |<--- 0x55 (測定) ----->|

```
 1. **Break Field送出:**
   送信ノードは、ハードウェア機能により規定長（マージンを見込み 13〜14 ビット時間相当）の Low 信号を送出する。
 2. **Break 検出:**
   受信側MCUは 11 ビット以上の連続 Low を検出した時点で「新フレーム開始」と判定し、オートボーレート待機状態へ遷移する。
 3. **Sync Byte (0x55) による校正:**
   続く 0x55 のエッジ幅から受信側MCUが内部ボーレートカウンタ（BAUD レジスタ）を自動補正する。
 4. **ペイロード受信:**
   直後に続くデータフィールドは、送信ノードの現在の実効レートに完全に同調した状態で安定して読み込まれる。
## 3. フレームフォーマット (Frame Structure)
送信ジッターを排除し、完全な決定論的ループを成立させるため、フレームは**完全固定長**とする。
```text
|<------------- 物理同期ヘッダ ------------->|<------------- 論理ペイロード ------------->|
[ Break Field ] [ Delimiter ] [ Sync Byte ]  [ TARGET_ID ] [ SENDER_ID ] [ DATA (M bytes) ] [ CRC ]
 (>=13 bit 0)    (>=1 bit 1)     (0x55)        (Next_ID)     (My_ID)         (固定長)       (CRC-8/16)

```
 * **TARGET_ID:** バトンを渡す相手（次に発話するノード）のID
 * **SENDER_ID:** 現在パケットを送出している自機のID
 * **DATA:** 制御データ、入出力状態、ステータスフラグ
 * **CRC:** 誤り検知用コード。破損時はタイマーリセットを行わずパケットを即破棄する。
## 4. ノード基本設計（Node Architecture）
### 4.1 パラメータ構成
各ノードが保持するネットワーク情報は以下の2点のみとする。システム全体のトポロジーやノード総数を認識する必要はない。
 * MY_ID（自機の識別ID）
 * NEXT_ID（次にバトンを渡すべき走者のID）
### 4.2 動作の3原則
 1. **バトンの受領と継承:**
   CRCが一致した正常フレームを受信し、かつ TARGET_ID == MY_ID の場合、即座に自身のデータを付与したフレーム（TARGET_ID = NEXT_ID）を送信する。
 2. **再送権限の剥奪（No-Retry Principle）:**
   宛先ノードが応答しない場合やCRCエラーを検知した場合でも、**スキップ処理や再送要求を絶対に実行してはならない**。
 3. **沈黙＝受動的安全（Silence is Safety）:**
   バス上で正常フレームが途絶え、内蔵タイマーが満了（規定時間超過）した場合、**無条件でアクチュエータ出力を安全遮断（STO）し、沈黙を保つ**。
## 5. メディエーター設計（Mediator Architecture / Option）
メディエーターは通常運行に不可欠な存在ではなく、信頼性と保守性を拡張するためのアタッチメントである。
```text
[ 通常時: 自律分散リレー ]
Node 1 ──> Node 2 ──> Node 3 ──> Node 1 ──> ...
   ▲
   └───── Mediator（無音でバスを傍受・診断データを蓄積）

[ 介入時: 意図的衝突と再点火 ]
1. Mediator がバスに強制 Break（ドミナント衝突）を注入
2. リレーが破綻し、全ノードが受動的安全待機へ移行
3. Mediator が新たな構成パケットを送出してリレーを再点火

```
 * **平常時（SNOOPモード）:**
   バスの通信を専有せず、パケットを傍受（スヌーピング）。バトンドロップの頻度、エラー率、脱落したノードの特定などをロギングし、予兆保全データとして上位システムへ提供する。
 * **異常・保守時（RE-IGNITE / COLLIDEモード）:**
   * **再点火:** ノイズ等の偶発的な要因でバトンが落ちた際、メディエーターがBreak ＋ Sync ＋ 指定IDパケットを打ち込んでリレーを復旧させる。
   * **ホットスワップ・構成変更:** 活線挿抜を行う際、メディエーターがバスに意図的な信号衝突を発生させて全員を一旦安全に停止させた後、対象ノードを除外した新しい NEXT_ID を指定して再点火する。
