# ADX Core-D DROP-Bus (TC-D1-01) スケッチ実装ガイドライン

本ドキュメントは、ATtiny1616を用いた半二重RS-485ネットワークにおいて、送信機（Node 1）および受信機（Node 2）の安定動作を担保するための実装ルールをまとめたものです。これまでの検証とデバッグを通じて確立された必須の要件を記載しています。

## 1. 共通アーキテクチャ
* **単一スケッチ構成**: `#define ROLE_TX` の有無により、同一のソースコードから各ノード用のバイナリを切り替えてビルドする構成を維持します[cite: 2]。
* **デバッグラインの分離**: マスター機の対話シリアルモニタには `SoftwareSerial` (PB4/PB5) を使用し、RS-485バス (USART0: PA1/PA2) と完全に通信ラインを分離します[cite: 2]。

## 2. 送信機 (Node 1 / Master) の実装ルール
* **Serialクラスの実績利用**: 送信側は手軽さと安定性の観点からArduino標準の `Serial` オブジェクトを利用し、`Serial.swap(1)` を用いてUSART0のピンをPA1(TX)/PA2(RX)へリマップします[cite: 2]。
* **バッファの完全フラッシュ**: RS-485トランシーバの送信イネーブル (`DE`) をLOW (受信モード) に戻す前には、**必ず `Serial.flush()` を実行**します[cite: 2]。これを怠ると、シフトレジスタ内の末尾バイトが送出される前にバスが遮断され、パケット破損の原因となります[cite: 2]。
* **Break信号の送出シーケンス**: BreakをGPIOトグルで送出する際は、①`Serial.flush()`による待機、②USART TXの一時無効化、③GPIOによるLOW/HIGH駆動、④USART TXの再有効化、の順序を厳格に守ります[cite: 2]。

## 3. 受信機 (Node 2 / Slave) の実装ルール
* **Serial.begin() の完全排除**: 受信機側において `Serial.begin()` を呼び出すと、Arduinoコア内でUARTのRX割り込みハンドラが自動登録されます[cite: 2]。これにより受信フラグが勝手にクリアされる競合バグを防ぐため、スレーブ機では `Serial.begin()` は一切使用せず、`PORTMUX` および `PORTA` レジスタを直接操作して初期化します[cite: 2]。
* **厳格なRXレジスタ読み出し順序**: 受信レジスタはFIFO構造となっており、**必ず先に `USART0.RXDATAH` (ステータス・エラーフラグ) を取得してから、`USART0.RXDATAL` (データ本体) を読み出します**[cite: 2]。低バイトを先に読むとFIFOポインタが進み、正しいステータスが取得できません[cite: 2]。
* **ボーレート設定の丸め誤差回避**: レジスタに `BAUD` を直接設定する計算式では、整数丸めによる切り捨て誤差を防ぐため、割り算より先に乗算を行う `(64UL * F_CPU) / (16UL * BAUDRATE)` を用います。
* **低速I/O回避のためのバッファリング**: SoftwareSerialによるPCへの文字出力処理は、ハードウェアUARTの受信速度に対して非常に低速です。ポーリング受信ループ内ではデータの配列格納のみに専念し、無音期間（50ms超過等）を検出してから一括でダンプ出力を行います。
