## The Field Reality: The Death of WebSerial on Mobile

In our [last project log](https://hackaday.io/project/205547-adx-enclosure-native-modular-hardware-standard/log/252238-the-6-month-silence-what-actually-happened), we celebrated our "Half-Baud Pulse Trick." It was a neat firmware hack that allowed a standard desktop browser tab, talking through a generic USB-RS485 dongle via the WebSerial API, to reliably trigger bootloader entries without proprietary UPDI debuggers.

On a developer workstation running Chrome on Linux or macOS, it worked like a charm.

Then we took the setup into the field.

Picture the actual use case for ADX: you are standing on a stepladder in front of a dust-covered control cabinet on a factory floor. You don't want to balance an open, \$2,000 laptop on one knee while fiddling with cables. You pull out an Android smartphone, plug in a short USB-C OTG cable, open a Web PWA, and hit "Update Firmware."

Except you can't.

Mobile Chrome on Android does **not** support the WebSerial API out of the box. Google has left it gated behind flags or outright disabled on mobile builds for years. WebUSB was our next candidate, but WebUSB on mobile introduces an endless maze of OS permission prompts, WinUSB driver conflicts on PCs, and vendor-class mismatches.

We hit an engineering wall: how do you build a zero-install, plug-and-play browser interface that talks raw binary to industrial field buses across Windows, Mac, Linux, and Android—without requiring users to compile native drivers, side-load APKs, or install special software?

## 1. The 1983 Epiphany: Web MIDI SysEx as a Universal Tunnel

The answer wasn't a shiny new web standard. It was a standard finalized in **1983**: the **MIDI 1.0 Specification**.

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   THE BROWSER-TO-FIELD BRIDGE                          │
├────────────────────────────────────────────────────────────────────────┤
│  [ Chrome / Edge (Android, PC, Mac) ]                                  │
│         │                                                              │
│         │  navigator.requestMIDIAccess({ sysex: true })                │
│         ▼                                                              │
│  [ Standard USB-MIDI Class Driver ] (Built-in to ALL major OSs since 90s)│
│         │                                                              │
│         │  7-to-8 Bit Packed SysEx Stream (31 ~ 50 KB/s)               │
│         ▼                                                              │
│  [ RPR4 Smart Probe (RP2040) ]                                         │
│         │                                                              │
│         │  Hardware PIO: 13-bit Dominant Low (112.0 μs LIN BREAK)     │
│         ▼                                                              │
│  [ ADX 20-Pin Bus (RS-485 LN-485 Frame) ] ──> [ Target: ATtiny1616 ]  │
└────────────────────────────────────────────────────────────────────────┘
```

Every desktop and mobile operating system on the planet—Windows, macOS, Linux, iOS, and Android—includes an in-kernel, class-compliant **USB Audio/MIDI driver**. When you plug in a USB-MIDI device, no driver installation wizard ever pops up. It just works.

Furthermore, the W3C **Web MIDI API** (`navigator.requestMIDIAccess({ sysex: true })`) is fully supported on modern Chromium-based browsers, including mobile Android.

### The 7-Bit Barrier: 7-to-8 Bit Packing
MIDI bytes are strictly 7-bit (`0x00`–`0x7F`); any byte with the most significant bit set (`0x80`–`0xFF`) is reserved for status messages. To pipe raw 8-bit firmware images through MIDI, we implemented a standard 7-to-8 bit packing routine:

```c
// Grouping seven 8-bit bytes into eight 7-bit MIDI SysEx data bytes
void sysex_pack_7to8(const uint8_t *src, size_t src_len, uint8_t *dst, size_t *dst_len) {
    size_t s = 0, d = 0;
    while (s < src_len) {
        uint8_t chunk = (src_len - s >= 7) ? 7 : (src_len - s);
        uint8_t msb_byte = 0;
        for (uint8_t i = 0; i < chunk; i++) {
            if (src[s + i] & 0x80) msb_byte |= (1 << i);
            dst[d + 1 + i] = src[s + i] & 0x7F;
        }
        dst[d] = msb_byte;
        s += chunk;
        d += (1 + chunk);
    }
    *dst_len = d;
}
```

We benchmarked this over TinyUSB on an RP2040. Blasting 16 KB of raw firmware data in 64-byte chunks achieved a sustained throughput of **30.97 KB/s** (517 ms total). With 256-byte chunks, it hit **50.41 KB/s**—with exactly **0.00% packet loss** across 256 continuous round-trips.

> **Key Takeaway:** When modern browser hardware APIs become fragmented or blocked by vendor politics, look at legacy class-compliant standards. USB-MIDI is effectively a high-speed, zero-driver raw packet conduit hiding in plain sight.

## 2. Fast-Tracking on the Bench: Pico H + Waveshare 2CH-RS485

Rather than waiting weeks for a custom PCB spin of our planned **RPR4 Smart Probe**, we grabbed off-the-shelf hardware to validate the protocol pipeline immediately: a **Raspberry Pi Pico H** seated into a **Waveshare Pico-2CH-RS485 shield** (dual SP3485 transceivers).

![ADX RPR4 Pre-development Bench](2026-11-02-pico-rs485-bench.jpg "Fig 1: Benchtop bring-up of the RPR4 Smart Probe pre-development rig: Raspberry Pi Pico H paired with a Waveshare 2CH RS-485 shield running hardware-level loopback tests.")

Before flashing any code, we tore down the Waveshare schematic to inspect its "automatic direction control" circuit.

![Waveshare Pico-2CH-RS485 Auto-Direction Circuit](2026-11-02-autodir-schematic.png "Fig 2: Waveshare 2CH RS-485 auto-direction circuit teardown showing the inverter transistor driving DE/~RE with DI tied to ground.")

Many cheap RS-485 converters use an RC one-shot timer circuit that automatically flips back to receive mode after a few microseconds, making sustained low pulses impossible.

Here, the schematic showed something brilliant: the transceiver's `DI` pin is permanently tied to **GND**, and the RP2040's `TX` pin directly drives `DE/~RE` through an inverting transistor.
- When `TX` is **High (Idle)**, the driver is disabled, and pull-up/pull-down bias resistors hold the bus in **Recessive High**.
- When `TX` is **Low**, the transistor turns off, pulling `DE/~RE` High and actively driving the bus into **Dominant Low**.

Because there is zero capacitive timing delay, holding `TX` Low holds the differential bus Low indefinitely. We had the green light: this off-the-shelf shield could generate real automotive-grade LIN BREAK signals.

## 3. Precision Pulse Generation with RP2040 PIO

A LIN BREAK requires holding the bus Low for at least 13 bit-times (at 115,200 baud, that is $13 \times 8.68\,\mu\text{s} \approx 112.85\,\mu\text{s}$), followed by a 1-bit Recessive High delimiter.

Relying on software bit-banging or OS sleep timers to generate a $112\,\mu\text{s}$ pulse is a recipe for timing jitter. If an interrupt fires, your pulse stretches to $140\,\mu\text{s}$ and the target MCU aborts the sync window.

Enter the RP2040's secret weapon: the **Programmable I/O (PIO)** state machine.

```pico-pio
.program ln485_tx
.side_set 1 opt

; Run at 8 cycles per UART bit time
pull block
out x, 1            ; Read command bit from FIFO

jmp !x do_uart_byte ; If bit 0 == 0: regular 8N1 byte

; --- Output LIN BREAK: 13 bits Low + 1 bit Delimiter High ---
set y, 12           side 0   ; 13 bit times Dominant Low
break_loop:
    nop             [6]
    jmp y-- break_loop
set y, 0            side 1   ; 1 bit time Break Delimiter High
nop                 [6]
jmp done

do_uart_byte:
; Normal 8N1 transmission sequence...
```

To verify the timing without dragging out a heavy bench oscilloscope, we configured a second PIO state machine on Channel 1 (GP5) acting as a high-speed pulse timer clocked at 2.0 MHz ($0.5\,\mu\text{s}$ resolution).

- **Theoretical BREAK Duration:** $112.85\,\mu\text{s}$
- **Measured BREAK Duration:** **$112.00\,\mu\text{s}$** (an error of just **$-0.75\%$**)

A sub-one-percent timing accuracy, achieved completely autonomously in silicon without consuming a single cycle of the main ARM cores.

## 4. The Mystery of the 33rd Byte: A Hardware FIFO Trajectory

With PIO generating pristine BREAK waveforms, we cabled Channel 0 to Channel 1 (`A0 <-> A1`, `B0 <-> B1`, `GND <-> GND`) on the Waveshare terminal block for loopback testing.

We transmitted a 31-byte test payload: `"RPR4-PIO-RS485-LN485-TEST-2026"`.

The packet fired, the receive buffer was read, and... **Mismatch Error**.

```text
Expected (31B): "RPR4-PIO-RS485-LN485-TEST-2026\0"
Received (30B): "RPR4-PIO-RS485-LN485-TEST-2026"  <-- Null terminator missing!
```

The transmission was dropping exactly one byte from the tail of the message.

### Hunting Down the Ghost
We formed a hypothesis based on the silicon architecture of the RP2040:
1. The RP2040's hardware UART is an **ARM PrimeCell PL011**.
2. The PL011 has a dedicated hardware RX FIFO depth of **exactly 32 bytes**.
3. When a LIN BREAK is detected, the PL011 records a framing error and pushes a dummy `0x00` break marker into the FIFO.
4. Total incoming stream:
   $$\text{Total Bytes} = 1\,(\text{BREAK: } 0x00) + 1\,(\text{SYNC: } 0x55) + 31\,(\text{Payload}) = \mathbf{33\text{ Bytes}}$$

Because our test routine waited for the transmission to complete before reading the receive buffer, **the 33rd byte hit a full FIFO and was discarded by the silicon**.

### The Smoking Gun: UARTRSR Register
Instead of guessing, we inspected the raw hardware status register:

```c
uint32_t rsr = uart_get_hw(uart1)->rsr;
printf("UARTRSR: 0x%02X | OE (Overrun Error): %s\n", 
       rsr, (rsr & (1 << 3)) ? "YES (OVERRUN DETECTED!)" : "NO");
```

Output:
```text
2. Hardware Status Register (UARTRSR):
   - Raw Value (Hex): 0x08
   - OE (Overrun Error / FIFO Overflow) : YES (OVERFLOW DETECTED!)
```

Bit 3 (`OE`) was set. To map the boundary with absolute precision, we ran a packet sweep test from 8 to 64 bytes:

| Payload Size | Total TX Bytes | Total RX Bytes | Hardware OE Flag | Verification Result |
| :---: | :---: | :---: | :---: | :--- |
| **8 B** | 9 B | 10 B | `OE = 0` | ✅ **PASS** |
| **16 B** | 17 B | 18 B | `OE = 0` | ✅ **PASS** |
| **30 B** | 31 B | **32 B** | `OE = 0` | ✅ **PASS (Exact FIFO Boundary)** |
| **31 B** | 32 B | **32 B** | `OE = 1` | ❌ **FAIL (33rd byte truncated)** |
| **32 B** | 33 B | **32 B** | `OE = 1` | ❌ **FAIL** |
| **64 B** | 65 B | **32 B** | `OE = 1` | ❌ **FAIL** |

The silicon was behaving exactly as specified. The cliff was real, repeatable, and down to the single byte.

## 5. The Automotive Compromise: The 8-Byte Fixed Frame

We could have solved this in software by adding high-priority RX interrupts or DMA streaming on the host MCU. But that would miss the larger point of robust protocol design: **you design protocols around the worst hardware in your network, not the best.**

On the other end of this RS-485 bus sits our target node: an **ATtiny1616** running a bare-metal bootloader. The ATtiny's USART has an RX buffer depth of just **2 bytes**, and the entire chip has only 512 bytes of SRAM. Asking a tiny 8-bit MCU to handle 64-byte variable-length packets under bus noise is asking for disaster.

Instead, we looked to the automotive industry. Both **LIN 2.x** and **CAN 2.0** converged on the same golden number decades ago: **8-byte fixed data payloads**.

```text
┌──────────────────────────────────────────────────────────────┐
│                  LN-485 STANDARD FRAME (12 Bytes)            │
├─────────┬─────────┬──────────────┬────────────────┬──────────┤
│  BREAK  │  SYNC   │ PID/Command  │ Data Payload   │ Checksum │
│ 13b Low │  0x55   │ (1 Byte)     │ (8 Bytes)      │ (1 Byte) │
│ (≒0x00) │ (1 Byte)│              │                │          │
└─────────┴─────────┴──────────────┴────────────────┴──────────┘
```

Adopting a strict 8-byte payload structure unlocked four massive advantages:

1. **Guaranteed Zero FIFO Overrun:** At 12 total bytes per frame, the packet occupies just $37.5\%$ of the PL011's 32-byte FIFO. Two full frames can queue up without a single dropped bit.
2. **Bit-Shift Math on ATtiny:** The flash page size of an ATtiny1616 is 64 bytes. Dividing 64 by 8 equals exactly **8 frames per page**. Because $8 = 2^3$, the bootloader needs zero division or modulus math. It indexes pages using simple right-shifts (`>> 3`) and bitwise masks (`& 0x07`), saving precious bytes of flash memory.
3. **Noise Immunity:** In electrically noisy industrial environments, shorter frames dramatically lower the probability of bit flips caused by motor EMI. If a frame fails its LIN 2.x enhanced checksum, retransmitting 8 bytes costs virtually nothing.
4. **Throughput:** At 115,200 baud, flashing a full 16 KB application image across 8-byte frames takes approximately **2.35 seconds** of raw wire time.

### The Proof: 1,000 Continuous Packets
We implemented the 8-byte frame parser and subjected the Pico loopback test to a continuous 1,000-packet stress test:
